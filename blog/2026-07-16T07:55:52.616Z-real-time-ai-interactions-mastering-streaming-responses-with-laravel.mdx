description: "In the first post of this series we built a working AI chatbot in Laravel. It had one problem every user notices immediately: you send a message, then stare at a spinner for five seconds while the whole response generates.
LLMs produce text token by token. If you wait for the full completion before showing anything, you're throwing away the single biggest UX win available: streaming. The same answer that takes 5 seconds to finish starts appearing in ~300ms when streamed. Nothing about the model got faster — but to the user, it feels 10x faster.
In this post we'll upgrade the chatbot to stream responses with Server-Sent Events (SSE) — no WebSockets, no Pusher, no extra infrastructure. Just Laravel.
WebSockets are bidirectional and need a long-running server (Reverb, Soketi) or a paid service. For chat completions you only need one direction: server → browser, for the lifetime of one request. That's exactly what SSE is for, and since Laravel 11 it's built into the framework as response()->eventStream().
Rule of thumb: presence, typing indicators, multiplayer → WebSockets. Streaming one AI answer → SSE.
We keep the ChatService from part 1 and add a streaming method. The openai-php client exposes createStreamed(), which returns an iterator of deltas:
<?php

namespace App\Services;

use Generator;
use OpenAI\Laravel\Facades\OpenAI;

class ChatService
{
    // ... SYSTEM_PROMPT and reply() from part 1 ...

    /**
     * @param array<int, array{role: string, content: string}> $history
     */
    public function streamReply(array $history, string $userMessage): Generator
    {
        $stream = OpenAI::chat()->createStreamed([
            'model' => 'gpt-4o-mini',
            'messages' => [
                ['role' => 'system', 'content' => self::SYSTEM_PROMPT],
                ...$history,
                ['role' => 'user', 'content' => $userMessage],
            ],
            'max_tokens' => 500,
        ]);

        foreach ($stream as $response) {
            $delta = $response->choices[0]->delta->content;

            if ($delta !== null) {
                yield $delta;
            }
        }
    }
}

A Generator is the right return type here: the controller can forward chunks as they arrive without ever holding the full response in memory.
Laravel 11.19+ ships response()->eventStream(), which handles the SSE formatting (event: / data: lines) for you:
<?php

namespace App\Http\Controllers;

use App\Services\ChatService;
use Illuminate\Http\Request;

class ChatStreamController extends Controller
{
    public function __invoke(Request $request, ChatService $chat)
    {
        $validated = $request->validate([
            'message' => ['required', 'string', 'max:2000'],
        ]);

        $history = $request->session()->get('chat_history', []);

        // CRITICAL: release the session lock. A streaming response is a
        // long-lived request — with the default file/database session
        // driver it would block every other request from this user
        // (including page loads!) until the stream finishes.
        $request->session()->save();

        return response()->eventStream(function () use ($request, $chat, $history, $validated) {
            $full = '';

            foreach ($chat->streamReply($history, $validated['message']) as $chunk) {
                $full .= $chunk;
                yield $chunk;
            }

            // persist history once the stream completes
            $history[] = ['role' => 'user', 'content' => $validated['message']];
            $history[] = ['role' => 'assistant', 'content' => $full];
            $request->session()->put('chat_history', array_slice($history, -20));
            $request->session()->save();
        }, headers: [
            'X-Accel-Buffering' => 'no', // tell nginx not to buffer the stream
        ]);
    }
}

Route it with the same throttling as part 1:
Route::post('/chat/stream', ChatStreamController::class)
    ->middleware(['auth', 'throttle:20,1']);

The native EventSource API only supports GET requests, and we need to POST a message body — so we read the stream with fetch instead:
<script>
async function streamChat(message, botEl) {
    const res = await fetch('/chat/stream', {
        method: 'POST',
        headers: {
            'Content-Type': 'application/json',
            'X-CSRF-TOKEN': document.querySelector('meta[name="csrf-token"]').content,
        },
        body: JSON.stringify({ message }),
    });

    const reader = res.body.getReader();
    const decoder = new TextDecoder();
    let buffer = '';

    while (true) {
        const { done, value } = await reader.read();
        if (done) break;

        buffer += decoder.decode(value, { stream: true });

        // SSE messages are separated by a blank line
        const events = buffer.split('\n\n');
        buffer = events.pop(); // keep the incomplete tail

        for (const evt of events) {
            const data = evt.split('\n')
                .filter(l => l.startsWith('data: '))
                .map(l => l.slice(6))
                .join('\n');

            if (data && data !== '</stream>') {
                botEl.textContent += data;
            }
        }
    }
}
</script>

</stream> is Laravel's default end-of-stream marker — filter it out (or customize it with the endStreamWith argument).
That's it. Send a message and watch the answer type itself out.
This is the part most tutorials skip. Streaming works instantly on php artisan serve, then mysteriously arrives all-at-once on your server. The culprit is always buffering somewhere between PHP and the browser:
nginx buffers proxied responses by default. The X-Accel-Buffering: no header above disables it per-response; alternatively set proxy_buffering off; for the route.
PHP-FPM + output buffering: check output_buffering in php.ini. Laravel's eventStream flushes after every yield, but an outer buffer can still swallow it.
Cloudflare / load balancers: most respect SSE content types, but verify with curl -N against production before blaming your code.
Debug tip: curl -N -X POST https://yourapp.test/chat/stream ... shows you exactly what arrives and when, with no browser magic in between.
Release the session lock before streaming (done above) — this is the #1 "my app hangs" bug with SSE in Laravel.
X-Accel-Buffering: no header for nginx (done above).
Timeouts: a stream can outlive max_execution_time and your web server's send timeout. Set both above your worst-case generation time (60s is a sane ceiling with max_tokens: 500).
Mid-stream errors: wrap the generator loop in try/catch and yield a friendly "Something went wrong" chunk — a dead stream with no message looks frozen to users.
Rate limit the endpoint (done above) — streaming doesn't change the fact that every request costs money.
Don't stream everything: for background jobs or short answers, the buffered endpoint from part 1 is simpler. Keep both.
Our bot streams beautifully, but it still only knows what's in its system prompt. Next up: RAG in Laravel — embeddings and pgvector, where we'll give it your actual documentation to answer from. Follow me to catch it.

### The Evolution of User Expectations in AI Chatbots

As artificial intelligence (AI) continues to permeate our daily interactions, user expectations regarding the responsiveness of AI chatbots have dramatically shifted. Users now anticipate immediate feedback, which is critical for maintaining engagement. Traditional methods of generating responses often involve waiting for the entire output to be computed before displaying anything. This can lead to frustrating delays, especially when working with large language models (LLMs) that generate text incrementally. By adopting real-time streaming capabilities, developers can transform the user experience, making interactions feel instantaneous and significantly more engaging.

### The Case for Server-Sent Events in Real-Time Applications

Server-Sent Events (SSE) provide a powerful mechanism for delivering real-time updates from the server to the client. Unlike WebSockets, which facilitate bidirectional communication and require more complex infrastructure, SSE focuses on unidirectional streaming. This is particularly beneficial for AI chatbots, where the primary need is to send incremental updates as they are generated. By utilizing SSE, developers can streamline their architecture, reducing overhead and simplifying the implementation of real-time features. The result is a more efficient system that enhances user experience without the complications associated with maintaining a persistent WebSocket connection.

### Comparing Streaming Protocols: SSE vs. WebSockets

While both SSE and WebSockets allow for real-time communication, they serve different use cases. WebSockets are ideal for applications requiring two-way communication, such as multiplayer gaming or collaborative editing. However, they introduce additional complexity, including the need for connection management and resource allocation. In contrast, SSE excels in scenarios where the server pushes updates to the client, such as in AI chatbots providing real-time responses. This simplicity allows developers to focus on delivering a seamless user experience without the overhead of managing a persistent connection.

### Implementing SSE in Laravel: A Step-by-Step Guide

Integrating SSE into a Laravel application is straightforward, especially with the built-in capabilities introduced in Laravel 11. Developers can create a controller that leverages the `response()->eventStream()` method to handle streaming responses. This method automatically manages the necessary headers and stream formatting, allowing developers to focus on the core logic of their application. Below is a sample implementation of a controller that streams responses from an AI chatbot:

```php
namespace App\Http\Controllers;

use App\Services\ChatService;
use Illuminate\Http\Request;

class ChatStreamController extends Controller
{
    public function __invoke(Request $request, ChatService $chat)
    {
        $validated = $request->validate([
            'message' => ['required', 'string', 'max:2000'],
        ]);

        $history = $request->session()->get('chat_history', []);
        $request->session()->save(); // Release session lock

        return response()->eventStream(function () use ($request, $chat, $history, $validated) {
            $full = '';

            foreach ($chat->streamReply($history, $validated['message']) as $chunk) {
                $full .= $chunk;
                yield $chunk;
            }

            // Persist chat history after streaming
            $history[] = ['role' => 'user', 'content' => $validated['message']];
            $history[] = ['role' => 'assistant', 'content' => $full];
            $request->session()->put('chat_history', array_slice($history, -20));
            $request->session()->save();
        }, headers: [
            'X-Accel-Buffering' => 'no', // Prevent Nginx from buffering the stream
        ]);
    }
}
```

### Session Management: Avoiding Common Pitfalls

Effective session management is crucial in a streaming context. When a streaming response is initiated, it can block other requests from the same user if the session lock is not released promptly. This can lead to a poor user experience, where subsequent interactions hang until the streaming response completes. To mitigate this, developers should ensure that the session lock is released as soon as possible, allowing other requests to be processed without unnecessary delays.

### Debugging Streaming Responses: Strategies for Success

Debugging streaming responses can be challenging, particularly in a production environment where buffering may occur at various points between the server and the client. One effective strategy is to use `curl` to simulate requests and inspect the raw output. The `-N` flag can be particularly useful for identifying whether responses are being buffered:

```bash
curl -N -X POST https://yourapp.test/chat/stream -H "Content-Type: application/json" -d '{"message": "Hello!"}'
```

Additionally, developers should implement logging within the streaming process to capture any errors or anomalies. By adding logging statements inside the generator, developers can track the flow of data and identify potential issues more effectively:

```php
Log::info('Streaming chunk: ' . $delta);
```

### Performance Optimization: Ensuring Smooth Streaming

When implementing SSE for AI chatbots, performance optimization is critical. Developers should be aware of potential bottlenecks, such as PHP-FPM output buffering and web server configurations (e.g., Nginx). Disabling output buffering in the PHP configuration and using appropriate headers to prevent Nginx from buffering responses can significantly enhance streaming performance. 

Furthermore, it is essential to configure the server's timeout settings to accommodate the expected duration of streaming responses. Setting the `max_execution_time` and web server's send timeout above the anticipated generation time can prevent premature termination of long-running requests. 

### Handling Mid-Stream Errors: Keeping Users Informed

Implementing robust error handling is essential for maintaining a smooth user experience. Wrapping the generator loop in a try/catch block allows developers to yield a friendly error message if an exception occurs during streaming. This ensures that users receive feedback rather than encountering a dead stream:

```php
try {
    foreach ($chat->streamReply($history, $validated['message']) as $chunk) {
        yield $chunk;
    }
} catch (\Exception $e) {
    yield 'Error: ' . $e->getMessage();
}
```
