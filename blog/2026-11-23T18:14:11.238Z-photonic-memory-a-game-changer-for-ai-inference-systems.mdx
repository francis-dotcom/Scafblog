description: "If you have ever run a long-context agent in production, you know the failure mode. The model is fine. The GPU is fine. Then the conversation grows, the KV cache grows with it, and suddenly your expensive accelerator is idle while the serving stack evacuates context to somewhere slow and recomputes it. The benchmark said you had enough FLOPS. Reality said you did not have enough memory within reach of the GPU.
For years the only answer was to buy a bigger GPU or shard the model across more of them. At Supercomputing 2026 in Chicago, a different answer went on display: move the memory out of the server and wire it to the GPUs with photonics.
On 16 November 2026, Penguin Solutions unveiled the MemoryAI Photonic Appliance, described by the company as the first photonics-based HBM-class memory appliance. It is built on Marvell's Photonic Fabric technology platform, which Marvell acquired from Celestial AI in a deal that closed on 2 February 2026.
The appliance is designed to let CPUs and GPUs transparently share disaggregated memory at HBM-class data rates, located metres from the accelerator rather than millimetres. According to the press release reproduced in full by IT Tech Pulse, the targets are:
57.6 Tbps of total appliance bandwidth — about 7.2 TB/s if you divide by eight.
Up to 16 TB of DDR5 RDIMM memory and 576 GB of HBM3E per appliance.
Three access modes: HBM Direct, HBM-DDR5 Cached and DDR5 Direct.
CPU access through CXL 3.0 and Marvell photonic NICs, with static or dynamic allocation managed by Penguin's software.
Marvell's own SC26 announcement put the appliance in a wider portfolio: Photonic Fabric memory modules, Structera X CXL 3.2 controllers, Teralynx switching silicon and 800G/1.6T active electrical cables. A CASRAI analysis adds numbers that appear nowhere in the primary release — up to 32 TB shared across 16 hosts with sub-350 ns near-NUMA latency, and up to 9 TB of expansion per Structera X controller. Treat those as a single-source claim, not a procurement specification.
Let me be blunt about the status of the headline figures. 57.6 Tbps, 16 TB and 576 GB are vendor targets published in one press release and repeated by several outlets. I have not seen an independent measurement. That does not make them useless; it means you should put them in the same bucket as a GPU vendor's peak FP4 number — useful for comparing architectures, useless as an acceptance test.
HBM is fast precisely because it is close. The stacks sit on an interposer next to the compute die, and the width of that connection is limited by the package and by how many I/O pins you can physically fit. That is why a GPU with a roomy HBM allocation still runs out of context: capacity is a packaging problem, not a silicon problem.
The photonic approach changes the medium. Instead of pushing electrical signals through copper traces and retimers as distances grow, optical I/O carries them across a fabric with far lower power per bit. The memory does not have to be soldered next to the die; it can live in another rack. From a systems point of view this turns memory from a component of a server into a service on a network — but one with latency and bandwidth characteristics much closer to local memory than to a storage call.
That distinction matters. Network-attached KV cache over conventional Ethernet saves you from recomputation but still feels like a remote call. A fabric designed for HBM-class traffic changes where you place the boundary between "hot" and "cold" context. You can keep a much larger working set live.
The appliance's three access modes are worth reading as an architectural menu rather than as marketing labels.
HBM Direct gives the fastest path. Use it for the active working set — the tokens being generated right now, the hot layers of the KV cache, the parts of a model that cannot tolerate a queue. DDR5 Direct trades bandwidth for capacity: this is where you park long conversational history, retrieved documents and intermediate agent state that will probably be needed again but not in the next millisecond. HBM-DDR5 Cached sits between them and lets the management software decide what stays hot.
If you are building an agent that performs dozens of tool calls per user request, that mapping is the interesting part. Most agent workloads are not compute-bound during tool calls; they are waiting on data movement and history reconstruction. Giving each tier an explicit home is a more direct lever on time-to-first-token than another increment of peak FLOPS.
Recent runtime work points in the same direction. The vLLM 0.34.0 release, for example, turned extensible KV cache on by default and changed the guidance on gpu_memory_utilization: in most cases you should no longer set it at all, letting the engine size the cache from memory that is actually free after warmup. That is a small configuration change with a large operational consequence — the runtime is becoming better at using whatever memory you give it, whether that memory is local or reached through a fabric.
Do not start with throughput. Start with the numbers that expose memory pressure:
KV cache eviction rate. If your engine is dropping context before the conversation ends, no amount of extra compute helps.
Time to first token at the 95th percentile. This is where recomputation shows up first.
Bytes moved per output token. A disaggregated setup can quietly turn a compute problem into a traffic problem.
Cache hit ratio across sessions. Reusable context is the economic justification for a shared pool.
Tail latency under concurrent long contexts. One long session is easy; fifty is a scheduling problem.
Then compare against a baseline on your own model and your own sequence-length distribution. The photonic fabric wins where context is reused and long; it is wasted on short, stateless requests where everything fits in local HBM anyway.
Moving bytes is not free. The IEA's World Energy Outlook 2026, published on 19 November, projects that data centre electricity use could double to 1,000 TWh per year by 2030, with related emissions rising around 70 per cent according to reporting by Euronews. The agency names grids, supply chains and public acceptance as the binding constraints.
This is why memory localisation and memory movement deserve attention from the power team, not just the platform team. Every byte you fetch from a distant pool costs energy in the optical links, the switches and the NICs. Every context you avoid recomputing saves the far larger energy of running the model again. A well-designed memory hierarchy is an energy optimisation as much as a latency optimisation — and in a world where grid connections are the scarce resource, that may be the more valuable one.
The unit of capacity planning is changing. It used to be the GPU: pick a part, count how many you can afford, multiply by a utilisation figure. Then it became the rack: power, cooling and network included. Now there is a third layer — the memory fabric — and a fourth — the grid connection behind it.
If you are designing an inference platform for 2027, write down four numbers before you choose an accelerator: how much hot memory you need, how much warm context you accumulate per active session, how many bytes per second your fabric must sustain, and how many megawatts the site can actually deliver. The announcements from SC26 suggest you can buy all four separately now. The engineering work is in making them behave like one machine...."

### The Long-Context Dilemma in AI Inference

AI inference systems, particularly those utilizing large language models (LLMs), encounter significant challenges when managing long-context scenarios. As the context length increases, memory requirements can surpass available resources, leading to performance degradation. This often results in increased latency or idle processing units as the system struggles to manage the growing context efficiently. Traditional solutions, such as augmenting GPU resources or sharding models, are not always feasible or cost-effective, underscoring the urgent need for innovative memory solutions that can adapt to these demands.

### Constraints of Traditional Memory Solutions

Conventional memory architectures, primarily reliant on electrical interconnects, exhibit limitations in bandwidth and latency. High Bandwidth Memory (HBM) provides substantial throughput but is limited by its physical proximity to processing units. As memory demands grow, scaling options become restricted, leading to bottlenecks. Moreover, the reliance on copper traces for data transfer introduces additional latency and power consumption, further complicating the challenges faced by AI inference systems that require rapid access to extensive datasets. The inherent constraints of these traditional memory solutions highlight the need for a paradigm shift in memory architecture.

### Photonic Memory: An Innovative Approach

Photonic memory technology offers a transformative approach to memory management in AI systems. By utilizing optical signals for data transmission, photonic memory achieves significantly higher bandwidths while simultaneously reducing power consumption. The MemoryAI Photonic Appliance, introduced by Penguin Solutions, exemplifies this innovation. This appliance allows for disaggregated memory to be accessed at HBM-class speeds, enabling CPUs and GPUs to share memory resources over distances that were previously impractical. This shift from electrical to optical interconnects not only enhances performance but redefines memory as a service rather than a fixed server component.

### Specifications of the MemoryAI Photonic Appliance

The MemoryAI Photonic Appliance boasts impressive specifications tailored for AI inference workloads. With a total bandwidth of 57.6 Tbps and the capability to support up to 16 TB of DDR5 RDIMM memory and 576 GB of HBM3E, it is designed to meet the rigorous demands of modern AI applications. The appliance supports three distinct access modes: HBM Direct, DDR5 Direct, and HBM-DDR5 Cached, each optimized for specific workloads. This flexibility in memory management ensures that critical data is readily accessible while optimizing overall system efficiency.

### Understanding the Access Modes for Optimal Performance

A thorough understanding of the operational implications of the three access modes is essential for optimizing AI inference performance. HBM Direct provides the fastest access for the active working set, making it ideal for real-time token generation and hot layers of the key-value (KV) cache. Conversely, DDR5 Direct offers larger capacity for long-term storage of conversational history and intermediate states, albeit with reduced bandwidth. HBM-DDR5 Cached serves as a hybrid solution, allowing dynamic management of memory resources based on usage patterns. This nuanced approach to memory allocation can significantly influence time-to-first-token metrics, which are critical for user experience in interactive applications.

### Enhancing Energy Efficiency and Reducing Latency

Transitioning to photonic memory not only addresses bandwidth limitations but also presents opportunities for enhanced energy efficiency. Traditional memory access incurs substantial energy costs, particularly as data is transferred across networks. The optical links employed in photonic memory reduce these costs, enabling more efficient data transfers. However, it is crucial to consider the trade-offs involved. While photonic memory can lower the energy required for data access, the overall system design must balance this against the energy demands of running complex AI models, particularly in large-scale deployments.

### Practical Implementation Considerations for Photonic Memory

Implementing photonic memory in AI systems necessitates careful consideration of several factors, including system architecture, workload characteristics, and existing infrastructure. Organizations must assess their memory needs, particularly in terms of hot and warm context requirements, to effectively leverage the capabilities of the MemoryAI Photonic Appliance. Additionally, understanding the implications of latency and bandwidth on user experience is critical. For example, applications with high KV cache eviction rates may benefit significantly from the rapid access provided by photonic memory, while those with short, stateless requests might not experience the same level of improvement.

### Case Study: Deploying Photonic Memory in Customer Support AI

A practical example of deploying photonic memory can be observed in a large-scale conversational AI system designed for customer support. This system processes thousands of simultaneous inquiries, necessitating efficient memory management to maintain responsiveness. By integrating the MemoryAI Photonic Appliance, the organization achieved a significant reduction in latency and improved cache hit ratios. The system architecture was adjusted to utilize HBM Direct for active sessions while leveraging DDR5 Direct for storing historical context. This strategic allocation of resources led to a marked improvement in time-to-first-token metrics, ultimately enhancing user satisfaction and operational efficiency.

### Future Implications for AI Infrastructure Design

As AI systems continue to evolve, the implications of adopting photonic memory technology extend beyond immediate performance gains. The shift towards disaggregated memory architectures will likely redefine how organizations approach capacity planning and resource allocation. With the potential to scale memory independently of compute resources, organizations can optimize their infrastructure for both cost and performance. This evolution will necessitate a reevaluation of traditional metrics used for evaluating system performance, emphasizing memory pressure and context management as critical factors.

### Addressing Challenges and Limitations in Photonic Memory

Despite the promise of photonic memory, it is essential to acknowledge potential challenges and limitations. The initial investment in photonic infrastructure may be substantial, and organizations must weigh the benefits against their specific use cases. Additionally, the technology is still maturing, necessitating independent validation of performance claims to ensure reliability. Organizations must remain vigilant in monitoring the evolving landscape of memory technologies to make informed decisions regarding their infrastructure investments.

### Conclusion: The Path Forward for AI Inference Systems

The advent of photonic memory technology marks a significant milestone in the evolution of AI inference systems. By addressing the limitations of traditional memory architectures, photonic memory enables more efficient management of long-context applications, ultimately enhancing performance and user experience. As organizations explore the integration of this technology into their AI infrastructure, they must remain mindful of the operational implications and challenges that accompany such a transition. The future of AI inference will undoubtedly be shaped by innovations like photonic memory, paving the way for more advanced and capable systems.
