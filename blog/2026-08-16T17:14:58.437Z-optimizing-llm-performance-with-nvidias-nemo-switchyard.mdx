description: "Earlier this week I benchmarked three local models on agent tasks and landed on a rule: keep the small model in the loop for the routine work, and escalate to a big one only when a step actually needs to think. The obvious follow-up question was who does the escalating. My honest answer was "some if-statements I haven't written yet."
Two days later NVIDIA open-sourced NeMo Switchyard, a Rust proxy that routes LLM traffic across models — including a judge-latched escalation router that starts every conversation on a weak model and promotes it to a strong one when an LLM judge decides the conversation deserves it. That's not approximately my conclusion; it's exactly my conclusion, productized. So I spent the afternoon wiring it up to the ollama models already on my Mac.
It worked, eventually, and the eventually is half the story.
The quick start says to install with uv tool install --python 3.10 "nemo-switchyard[cli]". That command fails: the package requires Python 3.12 or newer, and the docs pin 3.10. Drop the flag and it installs.
Then switchyard serve crashed with No module named 'yaml'. The CLI extra doesn't declare pyyaml. Adding it got me to the next crash — No module named 'uvicorn'. The incantation that finally worked:
uv tool install --force --with pyyaml --with uvicorn --with fastapi "nemo-switchyard[cli]"

This is launch-week open source in its natural state, and I don't say that meanly — the Rust core is clearly where the engineering went, and the Python packaging will catch up. But if you try it this week, now you know.
The docs describe a TOML config for the Rust server path. The Python CLI's serve command wants something else: a YAML "route bundle" with --routing-profiles, and I couldn't find that format documented anywhere. I ended up reading the installed package's route_bundle.py to learn the shape. Five route types are registered; the one I wanted was escalation_router, which takes weak, strong, and judge targets. This got a proxy serving on port 4000:
routes:
  local:
    type: escalation_router
    weak:   {model: llama3.2:3b, base_url: http://localhost:11434/v1, api_key: ollama}
    strong: {model: qwen3:14b,   base_url: http://localhost:11434/v1, api_key: ollama}
    judge:  {model: llama3.2:3b, base_url: http://localhost:11434/v1, api_key: ollama}
    fallback_target_on_evict: weak

Note the judge is the 3B. A small model deciding when a conversation is too hard for small models — we'll see how that went.
The route shows up at /v1/models as an OpenAI-compatible model called local, so any client that speaks the OpenAI API can use it unmodified. First request through the proxy took 3.8 seconds against 0.2 direct — one-time warmup. After that, warm proxy calls were 0.18–0.30s against 0.16–0.18s direct. Call it under a tenth of a second of overhead: for local routing, effectively free.
Simple questions came back from llama3.2:3b — the response's model field tells you who actually answered, which makes the whole thing pleasantly inspectable.
Then I tried to trigger the interesting part. A four-turn conversation of moderate difficulty stayed on the 3B throughout — the judge only starts evaluating at turn three by default, and needs two consecutive escalate verdicts, so early promotion is deliberately hard. (Those thresholds exist in the config model but aren't exposed in the YAML, so you live with the defaults for now.)
So I picked a fight: a seven-turn conversation that starts at "implement a lock-free MPMC queue" and ratchets through hazard pointers, linearizability proofs, and a TLA+ spec, with me rejecting every answer as insufficiently rigorous.
turn 1: model=llama3.2:3b  wall=1.9s
...
turn 6: model=llama3.2:3b  wall=3.8s
turn 7: model=qwen3:14b    wall=21.0s


Turn seven, the judge folded and promoted the session to the 14B — a one-way latch, so the conversation stays on the strong model from there. The proxy's /v1/stats endpoint shows token accounting for both models. Everything ran on my laptop; nothing left the house; the total cost of all of this was electricity.
Whether turn seven was the right moment is a fair question — I'd have escalated around turn three, when the answers first got hand-wavy. A 3B judging what exceeds a 3B is grading its own homework, and it grades generously. If the judge tuning gets exposed in the YAML, that's the first knob I'd turn.
Setup was rougher than the announcement suggests, the YAML is undocumented, and the judge is conservative to a fault. And still — this is the first tool I've used that treats "small model by default, big model on demand" as infrastructure instead of a blog-post aspiration. The pattern I was hand-rolling on Tuesday had a maintained Rust implementation by Friday. That's the part worth knowing about, whatever router you end up using.
If you know a cleaner way to expose the judge thresholds — or you've watched a bigger judge earn its keep — the comments are open.

### The Need for Intelligent Model Routing in AI Infrastructure

As large language models (LLMs) proliferate in various applications, the necessity for intelligent routing mechanisms in AI infrastructure becomes increasingly critical. With models varying significantly in size and capability, selecting the most appropriate model for a given task can greatly influence performance, resource utilization, and operational efficiency. This is particularly relevant when considering the deployment of LLMs in environments where latency and computational costs are paramount. NVIDIA's NeMo Switchyard emerges as a solution, providing a sophisticated framework for routing tasks between models based on their strengths and weaknesses.

### Understanding the Architecture of NeMo Switchyard

NVIDIA's NeMo Switchyard is a Rust-based proxy that facilitates the routing of LLM traffic among multiple models. At its core, it employs an escalation routing mechanism, which dynamically directs requests to either smaller or larger models depending on the task's complexity. This architecture allows for efficient resource allocation, ensuring that simpler tasks are handled by lightweight models, while more complex tasks are escalated to more powerful models only when necessary. The design emphasizes minimizing latency and maximizing throughput, which is essential for real-time applications.

### Step-by-Step Installation of NeMo Switchyard

Setting up NeMo Switchyard is a vital first step in harnessing its capabilities. Users may encounter challenges during installation, particularly with dependency management. The recommended command for installation is:

```bash
uv tool install --python 3.10 "nemo-switchyard[cli]"
```

However, this command may fail due to version mismatches. It is crucial to use Python 3.12 or newer. The corrected command is:

```bash
uv tool install --force --with pyyaml --with uvicorn --with fastapi "nemo-switchyard[cli]"
```

This command ensures that all necessary dependencies, including PyYAML and Uvicorn, are installed, which are essential for the proxy server's operation. Additionally, users should verify that their environment meets the requirements for Rust and any other dependencies specified in the official documentation.

### YAML Configuration: Crafting Routing Profiles

After successfully installing NeMo Switchyard, the next step involves configuring it through a YAML routing profile. This profile specifies the models to be used and how requests should be routed among them. A sample configuration for an escalation router could look like this:

```yaml
routes:
  local:
    type: escalation_router
    weak:   {model: llama3.2:3b, base_url: http://localhost:11434/v1, api_key: ollama}
    strong: {model: qwen3:14b,   base_url: http://localhost:11434/v1, api_key: ollama}
    judge:  {model: llama3.2:3b, base_url: http://localhost:11434/v1, api_key: ollama}
    fallback_target_on_evict: weak
```

In this configuration, the system starts with a weaker model for routine tasks and escalates to a stronger model when the complexity of the conversation increases. The judge model plays a pivotal role in evaluating whether escalation is warranted, ensuring efficient resource use.

### The Mechanics of the Escalation Routing Process

The escalation routing mechanism is the backbone of NeMo Switchyard's functionality. It assesses the complexity of ongoing conversations and determines whether to escalate tasks to a more capable model. The judge model evaluates the responses generated by the weaker model, deciding if they meet the required standards for more complex inquiries. This mechanism is designed to minimize unnecessary escalations while ensuring that tasks demanding higher cognitive capabilities are handled appropriately. 

### Benchmarking Performance: Routed Calls vs. Direct Model Calls

Performance benchmarking is essential to evaluate the effectiveness of NeMo Switchyard. By comparing direct model calls to routed calls, we can assess the overhead introduced by the routing mechanism. Initial tests indicate that while the first request through the proxy may exhibit a slight delay due to warm-up times, subsequent routed calls show minimal overhead compared to direct calls.

For example, initial requests may take around 3.8 seconds to process, but once warmed, typical response times for routed calls range from 0.18 to 0.30 seconds, while direct calls range from 0.16 to 0.18 seconds. This suggests that the routing mechanism introduces negligible latency, making it a viable solution for applications requiring real-time responses.

### Common Challenges and Troubleshooting Strategies

While the installation and configuration of NeMo Switchyard are conceptually straightforward, practical implementation can present several challenges. Users often report issues such as missing dependencies or configuration errors. For instance, the absence of PyYAML can lead to runtime errors, hindering the proxy's functionality.

To mitigate these challenges, it is essential to thoroughly review the installation documentation and ensure that all dependencies are correctly specified. Additionally, common troubleshooting strategies include:

1. **Dependency Verification**: Ensure all required packages are installed. If encountering module errors, check that PyYAML and Uvicorn are included in your environment.
   
2. **Configuration Validation**: Double-check the YAML routing profile for syntax errors or incorrect model specifications.

3. **Network Configuration**: Ensure that the base URLs specified in the routing profile are accessible and correctly configured.

4. **Log Monitoring**: Enable logging to track the routing decisions made by the judge model, which can help identify any misconfigurations or performance bottlenecks.

### Real-World Applications: Use Cases for NeMo Switchyard

The practical applications of NeMo Switchyard are extensive, ranging from customer service chatbots to complex data processing tasks. In a customer support scenario, a lightweight model can handle routine inquiries, while more complex issues can be escalated to a larger model. This approach not only optimizes resource usage but also enhances user experience by providing timely and accurate responses.

In data engineering tasks, NeMo Switchyard can facilitate the processing of large datasets by routing tasks to the appropriate models based on their capabilities. This dynamic allocation of resources ensures that computational power is utilized efficiently, reducing costs and improving throughput. For instance, a data processing pipeline can utilize smaller models for preprocessing tasks and escalate to larger models for analytical queries.

### Addressing Limitations and Future Enhancements

While NeMo Switchyard offers significant advantages, it is essential to acknowledge its limitations. For instance, the decision-making thresholds for the judge model are not currently exposed in the YAML configuration, which may lead to conservative escalation decisions. Users seeking more aggressive escalation may find themselves constrained by the default settings. Furthermore, the lack of transparency in how the judge model evaluates task complexity could lead to unpredictable performance in certain scenarios.

Future enhancements could include exposing these thresholds for user configuration, allowing for more tailored routing behavior. Additionally, integrating advanced machine learning techniques for predictive routing could enable even more intelligent decision-making processes, refining the model selection based on historical performance data and user interactions.
