Every line is one tool call the model chose to make. I wrote the program that produced it in one Python file with a single dependency, and I want to walk through each part, because once you can read a trace like this one, most of what people call agent frameworks stops being mysterious. One warning before we start: the answer this run gave me was wrong, and why is the most useful thing in the post.
I built this one to find out what a framework does for me before I let one do it. The answer turned out to be less than I expected. An agent is a loop around an API call, a handful of functions, and a few decisions about when to stop. Frameworks add real things on top, such as saved state, tracing and handoffs between agents, and I will say which of those are worth having near the end. But if you start there, you cannot tell which behavior comes from your design and which comes from the library.
The agent is a web research assistant. You ask it a question, it searches Wikipedia, fetches pages, saves notes about the claims it relies on, and answers with sources. It has four tools, it works against any OpenAI-compatible endpoint, and the whole thing is 331 lines including error handling. You need Python 3.10 or newer, uv, and either an API key or a local model through Ollama. The code is at github.com/iayanpahwa/research-agent-from-scratch, and every code block below is copied from that file by a script, not retyped. To run it:
export AGENT_API_KEY=...   # AGENT_BASE_URL and AGENT_MODEL default to OpenAI and gpt-4o-mini
uv run agent.py "Who coined the term 'prompt injection', and how is it different from jailbreaking?"

The trace prints to stderr and the answer to stdout. Set PRICE_IN_PER_MTOK and PRICE_OUT_PER_MTOK if you want the cost line to show a number, because they default to zero. The README covers OpenRouter and Ollama.
A chatbot makes one model call and returns the answer. A workflow makes several calls, but your code decides the order: search, then fetch the top result, then summarize. Anthropic's essay on building effective agents draws the line this way: agents are "systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." The model decides whether to search again, which page to open, and when it has enough.
That is the whole difference. In a workflow you can read the code and know what will happen. In an agent you can only read the code and know what is allowed to happen.

The agent here has six parts, and I will use the names the code uses.

run() is the loop. messages is the history the model sees on every call. call_model() sends one request to the API. TOOL_SCHEMAS describes the tools to the model, and TOOLS holds the functions that actually run. notes.db is a SQLite file that outlives the process. Everything in the next four sections is one of those parts.
The model never sees your Python. It sees a JSON description of each tool: a name, a sentence about what it does, and the parameters it takes. Here is the one for fetch_url, printed from the running program:

The description is the model's only guide to when to use the tool, so it is part of your design, not documentation. A vague description gets a tool called at the wrong time, or never. A small helper builds these descriptions, and the system prompt is where the agent's rules live:
def schema(name: str, description: str, **props: str) -> dict:
    return {
        "type": "function",
        "function": {
            "name": name,
            "description": description,
            "parameters": {
                "type": "object",
                "properties": {
                    k: {"type": "string", "description": v} for k, v in props.items()
                },
                "required": list(props) if name != "read_notes" else [],
            },
        },
    }

SYSTEM_PROMPT = """You are a research assistant. Answer the user's question using pages you fetch.
- Search first, then fetch the pages worth reading. Do not answer from memory.
- Save a note with save_note for each claim you rely on, with the page it came from.
- Check read_notes before searching, in case an earlier run already covered the topic.
- Stop when the question is answered. Give a short answer and list your sources."""

The function behind it is ordinary code, with two rules I would apply to any agent tool. First, it never raises. A tool that throws an exception takes the whole run down, so run_tool below catches everything, and a tool that returns {"error": "..."} hands the model something it can react to. Second, it assumes the model is careless or has been tricked, because it might be. Here are the checks at the top of fetch_url:
parsed = urlparse(url)
if parsed.scheme not in ("http", "https") or not parsed.hostname:
    return {"error": "only http and https URLs are allowed"}
if not is_public_host(parsed.hostname):
    return {"error": "refusing to fetch a private or unresolvable address"}

Only http and https, and only hosts that resolve to public addresses. Without the second check, a model that decides to fetch http://169.254.169.254/ would be asking your cloud provider's metadata service for credentials on your behalf.
I checked both with curl on October 23, and the tool sends the descriptive one. search_wikipedia is the only search tool because it needs no API key and it behaves. A paid search API is a one-function swap if you want better results, and it would not change anything else in the design.
fetch_url also does not follow redirects. It returns {"status": 308, "redirect_to": "..."} and lets the model decide to fetch the new address, which sends the next hop back through the same checks. In the trace at the top, the model hit exactly that on an OWASP link and followed it two steps later.
Talking to the model is one HTTP request:
def call_model(messages: list[dict]) -> dict:
    """One chat-completions request. Retry rate limits and server errors; raise anything else."""
    for attempt in range(4):
        r = httpx.post(
            f"{BASE_URL}/chat/completions",
            headers={"Authorization": f"Bearer {API_KEY}"} if API_KEY else {},
            json={"model": MODEL, "messages": messages, "tools": TOOL_SCHEMAS},
            timeout=120,
        )
        if r.status_code == 429 or r.status_code >= 500:
            time.sleep(2**attempt)
            continue
        r.raise_for_status()
        data = r.json()
        if "choices" not in data:
            raise RuntimeError(f"unexpected model reply: {str(data)[:200]}")
        return data
    raise RuntimeError(f"model API still failing after retries (HTTP {r.status_code})")

The retry is there because rate limits and server errors are normal, and a single 429 should not end a run. Everything else is a plain request to /chat/completions with the history and the tool descriptions attached.
for step in range(1, MAX_STEPS + 1):
    data = call_model(messages)
    msg, usage = data["choices"][0]["message"], data.get("usage") or {}

Read it as three cases. If the reply has no tool_calls, the model is done and its text is the answer. If it has tool calls, the loop runs each one and appends one role: tool message per call, tagged with the tool_call_id the model gave it. That tag is how the model matches results to requests, and if a call has no matching result message, the API rejects the next request. Then the loop goes around again with a longer history.
A reply can contain several tool calls at once. Step 3 of the trace has three fetches in one reply, and each gets its own result message. The function that runs one call is short:
def run_tool(call: dict) -> str:
    name = call["function"]["name"]
    try:
        args = json.loads(call["function"]["arguments"] or "{}")
        result = (
            TOOLS[name](**args) if name in TOOLS else {"error": f"no such tool: {name}"}
        )
    except Exception as exc:  # a tool must never end the run
        result = {"error": f"tool failed: {type(exc).__name__}: {exc}"}
    return json.dumps(result)

Malformed arguments, an unknown tool name and a tool that returns an error all come back to the model as data. The model usually corrects itself on the next step, and when it does not, the step cap in a later section ends the run.

The first kind of memory is the messages list. It is everything the model knows, it is sent in full on every call, and it only grows. In the trace above, the prompt was 300 tokens at step 1 and 12,109 at step 10. The total across all eleven calls was 69,823 input tokens, not because any single prompt was that large but because every call resends everything before it. The total grows faster than the number of steps.

Feeding raw HTML to a model wastes most of the window, and even the text of a long page is too much to keep. def save_note(topic: str, claim: str, source_url: str) -> dict:
    with closing(db()) as con, con:
        con.execute(
            "INSERT INTO notes (ts, topic, claim, source_url) VALUES (datetime('now'), ?, ?, ?)",
            (topic, claim, source_url),
        )
    return {"saved": True}

def read_notes(topic: str = "") -> dict:
    """Match any word of the topic against saved topics and claims."""
    words = [w for w in re.findall(r"[^\W_]+", topic) if len(w) > 2][:8] or [""]
    clause = " OR ".join("topic LIKE ? OR claim LIKE ?" for _ in words)
    params = [f"%{w}%" for w in words for _ in (0, 1)]
    with closing(db()) as con:
        rows = con.execute(
            f"SELECT topic, claim, source_url FROM notes WHERE {clause} ORDER BY id DESC LIMIT 20",
            params,
        ).fetchall()
    return {"notes": [{"topic": t, "claim": c, "source_url": s} for t, c, s in rows]}

The system prompt tells the model to check read_notes first and to save a note for each claim it relies on. I ran the same question twice against one database. My first version of read_notes matched the model's whole query as a single substring, so the second run asked for "prompt injection jailbreaking coined term", found nothing under the topic "prompt injection coinage", and started from scratch. That is the kind of bug you find only by running the thing twice. The version above matches on any word, and the second run now reads its earlier notes before it does anything else. The notes also carry a risk I only noticed when I read them back, which the cost section below shows.

A loop with no exit is a billing event. The agent here has four ways to stop. It stops when the model answers without asking for a tool, which is the normal case. It stops at a step limit. It stops when total tokens pass a budget. And it stops when something unrecoverable happens, such as a model API that keeps failing after retries. The limits are plain constants:
MAX_STEPS = 12
TOKEN_BUDGET = 60_000
MAX_TOOL_CHARS = 8_000
MAX_BYTES = 2_000_000

and the budget check sits at the bottom of the loop, using the usage field the API returns with every reply. It runs after tool steps, so the last model call can overshoot it, and the first run in this post did: its total was 71,659 tokens against a 60,000 budget, because the check passed at 59,136 after step 10 and the final answer call added the rest. A hard cap would check before each call.
if tokens_in + tokens_out > TOKEN_BUDGET:
    stop = "token_budget"
    break

The part people skip is deciding what the user sees at each exit. When a run stops at the step limit, it prints stop=max_steps and returns a message saying it stopped without an answer, rather than a half-finished sentence that reads like a result. Errors split into three groups. 
A bad tool call goes back to the model. A rate limit or server error is retried with a growing delay. Anything else ends the run. If you cannot say which group an error belongs to, the loop will eventually decide for you at an inconvenient time.

This is the section I would not skip. Look at what the agent you just built does: it takes text written by strangers, from any public page, and puts it in front of a model that can call tools. Humanbound's Demetris Gerogiannis ran a pricing agent with a fetch_url tool, much like ours, through 1,350 runs across nine models in One Link Away. A competitor page one link away carried the trap. Four of the five non-OpenAI models he tested sent a confidential unit cost to an attacker's server on every run when nothing in the system prompt addressed it. No jailbreak was involved.
Our research agent has the same exposure, and I would rather list it than hide it. A page can tell the model to do something. save_note writes to storage that persists, so a poisoned note can mislead every future run. fetch_url will request any public address, including one whose query string carries data out. The only things between the agent and a bad day are the step cap, the token budget and the address check, and that check has a known gap: it looks the name up once and the HTTP client looks it up again when it connects, so a hostile DNS server can pass the check and then point at a private address. A production agent should connect to the address it checked. That is acceptable for a research toy that can write only a local file. 
It stops being acceptable the moment you add a tool that sends email, runs code or touches money, because the worst case now grows with every tool you add.

### Understanding the Role of AI Agents in Modern Applications

AI agents have emerged as pivotal tools in various domains, acting as intermediaries that automate complex tasks through intelligent decision-making. These agents leverage machine learning models to perform operations such as data retrieval, analysis, and even interaction with users. The ability to create a custom AI agent tailored for specific tasks, such as web research, enables developers to explore the nuances of AI functionalities and limitations. By building an agent from scratch, one gains a comprehensive understanding of its architecture, decision-making processes, and potential pitfalls, contrasting starkly with the opaque nature of pre-built frameworks.

### Setting Up the Development Environment for AI Agent Creation

The absence of complex frameworks simplifies the installation process, allowing developers to focus on the core functionalities of their agent. ### Core Components of the AI Agent: An Overview

The architecture of an AI agent typically consists of several core components: the agent's loop, message handling, tool definitions, and persistence mechanisms. The agent's loop is responsible for managing the flow of execution, making decisions based on user input, and determining when to stop processing. Message handling involves maintaining a history of interactions, which informs the model's responses and decisions. Tool definitions specify the capabilities of the agent, such as fetching web pages or saving notes, while the persistence layer, often implemented with a database, allows the agent to retain knowledge across sessions. Understanding these components is crucial for effectively designing and implementing the agent.

### Implementing the Agent: A Step-by-Step Coding Process

The coding process for the AI agent begins with defining its main loop, which orchestrates the interaction between the user and the model. The loop continuously processes user queries, invokes the appropriate tools, and updates the message history. A simple yet effective implementation can be structured as follows:

```python
def run():
    messages = []
    while True:
        response = call_model(messages)
        # Process response and update messages
```

In this code snippet, `call_model` is a function that interacts with the AI model, sending the current message history and receiving the model's output. This modular approach allows for easy updates and modifications to the agent's behavior.

### Tool Implementation: Fetching and Saving Data

The agent's functionality is enhanced through the implementation of various tools. For example, a `fetch_url` tool retrieves web pages and extracts relevant content. This tool must handle errors gracefully, ensuring that the agent can recover from failed requests without crashing. Below is an example of a robust implementation for the `fetch_url` tool:

```python
def fetch_url(url: str) -> dict:
    if not is_valid_url(url):
        return {"error": "Invalid URL"}
    
    try:
        response = httpx.get(url)
        response.raise_for_status()
        return {"content": response.text}
    except httpx.HTTPStatusError as e:
        return {"error": f"HTTP error: {e.response.status_code}"}
```

In this implementation, the function checks the validity of the URL before making a request. It also captures any HTTP errors, returning a structured error message that the model can interpret.

### Testing the AI Agent: Validating Functionality and Performance

Once the agent is built, thorough testing is essential to validate its functionality. This involves running various queries and analyzing the results for accuracy and completeness. The agent should be able to handle different types of requests, including those that require multiple tool invocations. Performance can be measured in terms of response time, accuracy of fetched data, and the cost associated with API calls. ### Common Pitfalls and Error Handling Strategies

While developing an AI agent, several common pitfalls should be addressed proactively. One major risk is the overgeneralization of AI capabilities, which can lead to misconceptions about the agent's reliability.
