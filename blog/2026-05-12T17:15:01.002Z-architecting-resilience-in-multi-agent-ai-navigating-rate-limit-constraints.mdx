That creates a real problem for free-tier usage, because the primary model may allow only around 15 RPM. One user query can already exceed that ceiling, even when token usage is still well under the TPM limit. 
Instead of hardcoding a single model, I built a fallback queue.
The idea was simple:
Try the primary model first
If it hits a rate limit, move to the next model
Keep retrying until one succeeds
Show a small system notice in the UI when switching models
This way, the app can keep streaming responses instead of crashing on a 429 error. 
Here is the architecture powering the automatic model switching inside gemini_client.py:
import os
from google import genai
from google.genai import types

FALLBACK_MODELS = [
    "gemini-3.1-flash-lite-preview",
    "gemini-2.5-flash",
    "gemma-4-31b-it",
    "gemma-4-26b-a4b-it",
]

def _get_model_queue(use_pro: bool) -> list:
    """Returns a list of models to try in order."""
    primary = "gemini-2.5-pro" if use_pro else "gemini-2.5-flash"
    return [primary] + FALLBACK_MODELS

def generate_stream(prompt: str, system_prompt: str = "", use_pro: bool = False):
    """
    Streams a response with automatic failover to fallback models.
    """
    client = genai.Client(api_key=os.getenv("GEMINI_API_KEY"))
    models_to_try = _get_model_queue(use_pro)

    for i, model in enumerate(models_to_try):
        config, final_prompt = _build_config_and_prompt(model, prompt, system_prompt)

        try:
            if i > 0:
                yield f"<br><span style='color:#fbbf24; font-size:10px;'>[System: Primary RPM limit reached. Switching to {model}...]</span><br>"

            for chunk in client.models.generate_content_stream(
                model=model,
                contents=final_prompt,
                config=config,
            ):
                if chunk.text:
                    yield chunk.text

            return

        except Exception as e:
            error_msg = str(e)

            if "429" in error_msg or "RESOURCE_EXHAUSTED" in error_msg:
                if i < len(models_to_try) - 1:
                    continue
                yield "<span style='color:#f43f5e; font-weight:600;'>System overloaded. All backup models are currently busy. Please try again in a few minutes.</span>"

            elif "500" in error_msg or "internal" in error_msg.lower():
                break

When the primary model hits its RPM limit, generate_stream() catches the 429 error, skips to the next model, and retries the same prompt.
Because the fallback happens inside the streaming loop, the UI can show a tiny notice like this:
[System: Primary RPM limit reached. Switching to gemma-4-31b-it...]

The user does not get an ugly error screen. They just keep seeing the response stream normally.

### The Challenge of Multi-Agent Interaction

Designing multi-agent AI systems introduces significant architectural challenges, particularly in managing the interactions between multiple agents. Each agent may require several simultaneous requests to different models, leading to a rapid escalation of API calls. This complexity is exacerbated in environments with strict rate limits, such as Requests Per Minute (RPM) thresholds. When these limits are exceeded, it can result in service disruptions, degraded user experiences, and overall system unreliability. Understanding these dynamics is essential for developers aiming to build resilient and scalable AI applications.

### Defining RPM and TPM: The Critical Metrics

In the realm of AI applications, two key metrics dominate the landscape: Requests Per Minute (RPM) and Tokens Per Minute (TPM). RPM refers to the maximum number of API requests that can be executed in a minute, while TPM measures the total number of tokens processed during that same period. For instance, a single user query in a multi-agent system may trigger numerous requests, quickly consuming the available RPM. Understanding the balance between RPM and TPM is vital for developers, as exceeding RPM can lead to immediate service interruptions, regardless of whether token usage remains within acceptable limits.

### The Impact of High Request Rates on System Performance

The cumulative effect of multiple agents making simultaneous requests can overwhelm the available RPM. For example, in VerdictAI X, a single user query can trigger up to 21 requests due to the orchestration of five specialized agents. This scenario highlights the potential for hitting rate limits almost instantaneously, especially when using free-tier services that impose strict RPM constraints. Developers must architect resilient systems capable of accommodating such spikes in demand without compromising performance or user experience.

### Implementing a Dynamic Fallback Queue: A Strategic Solution

To address the challenges posed by RPM limitations, implementing a dynamic fallback queue can be an effective strategy. This approach allows the system to attempt a primary model first and, upon hitting a rate limit, seamlessly switch to a secondary model without interrupting user interactions. By designing the system to handle failures gracefully, developers can maintain service continuity even under constrained conditions. This strategy not only enhances reliability but also optimizes resource usage across different models, making it a critical component of resilient system design.

### Code Implementation of the Fallback Mechanism

from google import genai

FALLBACK_MODELS = [

This code snippet illustrates how to implement a fallback mechanism that allows the system to switch between models based on their availability. The `generate_stream` function attempts to stream responses from the primary model first, and if it encounters a 429 error indicating that the RPM limit has been reached, it switches to the next model in the queue. This design ensures that users continue to receive responses without experiencing service interruptions.

### User Experience During Model Switching: Best Practices

A critical aspect of implementing a fallback mechanism is ensuring a seamless user experience during model switching. The user interface should provide real-time feedback when a model switch occurs, such as displaying a notification that the system is transitioning to a backup model. This proactive communication helps manage user expectations and maintains engagement, reducing frustration associated with potential delays or errors. For instance, displaying a small notice like "[System: Primary RPM limit reached. Switching to gemma-4-31b-it...]" reassures users that the system is actively working to resolve the issue. Additionally, incorporating visual indicators, such as loading spinners or progress bars, can further enhance user experience during these transitions.

### Rigorous Testing and Optimization of the Fallback System

Once the fallback mechanism is implemented, rigorous testing is essential to ensure its reliability under various load conditions. This includes simulating high request rates to observe how the system behaves when it hits RPM limits. Performance metrics should be collected to assess the time taken for model switching and the overall user experience during these transitions. Optimization may involve fine-tuning the order of fallback models or enhancing error handling to minimize the impact of failures. Developers should also consider stress-testing the system to identify potential bottlenecks and areas for improvement. For example, conducting load tests that mimic real-world usage scenarios can help identify how the system performs under peak demand.
