description: "Hi Devs,
If you’ve connected an AI agent to a real database, you’ve probably felt the discomfort of the default approach: handing the model an execute_sql(sql) tool.
Read-only roles, SQL validation, allowlists, and prompt instructions all help. But they still give the model raw database authority and then try to constrain it.
I wanted the opposite: a boundary where the model never receives that authority in the first place.
So I built Synapsor Runner, an Apache-2.0 runtime that sits between an MCP client and PostgreSQL or MySQL. Instead of exposing SQL, it exposes reviewed semantic capabilities such as:
billing.inspect_invoice
billing.propose_late_fee_waiver
support.propose_plan_credit

No database. No signup.
npx -y -p @synapsor-runner audit --example dangerous-db-mcp
npx -y -p @synapsor-runner demo --quick

The audit flags risky MCP tool shapes, such as raw SQL execution.
The quick demo walks through the proposal → evidence → replay boundary. It explains and records that boundary; it does not claim to test a live database.
The model can read only the columns and rows that a contract allows. It can propose changes, but the model-facing MCP surface contains no approve tool and no apply tool.
Commit authority lives entirely outside the model loop.
Everyone does allowlists. The part I care about is that there is literally no tool the model can call to write.
This does not stop prompt injection.
What it does is contain the blast radius when injection—or simply a confused model—happens.
In my testing, I put a fleet of real LLM agents on one server. Several were given injection tasks such as:
“Read the other tenant’s data.”
“Ignore the budget.”
The result:
0 cross-tenant reads
0 unauthorized writes
That was not because the models resisted the prompts. It was because the boundary was enforced outside the models.
This is the same class of failure demonstrated in the recent Supabase MCP token-exfiltration example: a model is tricked into running attacker-controlled SQL. If there is no SQL tool and no commit tool to reach, that path closes.
Tenant scope, allowed columns, and allowed rows are fixed by the reviewed contract and trusted server-side context.
That context is bound outside the model’s arguments, never supplied through a tool parameter.
The model cannot widen what it sees.
A proposal records the requested before-and-after state but does not modify the source database.
Approval and writeback happen outside MCP.
When an approved proposal is applied, Runner rechecks:
Trusted tenant scope
Target row
Allowed columns
Expected row version
Operation bounds
Idempotency
Affected-row limits
A stale row becomes a conflict instead of a silent overwrite.
Every apply operation is recorded with a receipt and replay linkage.
By default, activity is stored in a local SQLite ledger.
A shared PostgreSQL runtime store is also available for multi-process deployments.
Not every change needs a human.
A contract can define tiered auto-approval for small, low-risk proposals:
AUTO APPROVE WHEN amount_cents <= 2500
LIMIT 20 PER DAY

Policies can also define aggregate value ceilings.
When a proposal exceeds a rule or budget, it falls back to human review, and the ledger records why.
Higher-risk capabilities can require approvals from multiple distinct people.
Policy approval still gives the model no commit authority. A trusted Runner worker performs the guarded write outside MCP.
For reviewed batch operations:
The selection rule is contract-defined, not model-generated.
Tenant scope is forced.
Row and value limits are declared.
Application is atomic.
Drift fails closed.
Receipts record the affected rows.
This is not a path to arbitrary UPDATE statements.
Runner can record a bounded inverse and create a separate compensation proposal.
Reverting is not rollback or time travel. It is another reviewed proposal that passes through the same approval and writeback boundary.
Contracts are portable JSON documents.
You can hand-author the JSON or use an optional SQL-like DSL with constructs such as:
CREATE AGENT CONTEXT
CREATE CAPABILITY
Approval policies
The DSL compiles to the same JSON format.
Either way, contracts can be reviewed and versioned in Git like application code.
This is a security tool, so I would rather under-claim.
Synapsor Runner:
Does not make arbitrary SQL safe
Does not prevent prompt injection
Does not replace least-privilege database roles
Does not replace restricted views
Does not replace row-level security
Does not replace staging data
It is a scoped enforcement boundary that limits what a compromised or mistaken model can read, propose, and change.
The built-in guarded path intentionally excludes:
Free-form or model-generated predicates
UPSERT
DDL
Unbounded writes
Multi-table transactions
External side effects
Those operations need an application-owned executor that is invoked only after approval, with the application retaining ownership of the transaction and security checks.
A side benefit is that this approach also tends to use fewer tokens.
Because the model calls semantic tools instead of writing SQL:
It does not need the database schema in context.
It does not need table and column dumps.
It avoids list_tables and describe_table round trips.
It avoids “write SQL → column error → retry” loops.
Typed arguments can fail before a database round trip.
Results are bounded by column allowlists and MAX ROWS.
Aggregate reads can return a scalar such as COUNT instead of sending many rows back into context.
Approval and writeback happen off-model, so those steps use zero model tokens.
There is a caveat: every capability appears in the model’s tools/list.
A contract that exposes hundreds of tools to one agent can lose the token savings through tool-definition bloat.
The real claim is:
Well-scoped contract → net cheaper
I would treat that as directional rather than a benchmarked number, but “safer and cheaper per run” appears to hold for the common case.

### The Security Dilemma of AI Database Access

The integration of AI agents with production databases raises significant security concerns. Traditional methods often involve granting these agents direct access to databases, which can lead to unauthorized data manipulation and exploitation through vulnerabilities like prompt injection. The challenge lies in balancing operational efficiency with robust security measures, necessitating a reevaluation of how AI agents interact with sensitive data.

### Understanding Scoped Access: A Fundamental Shift

Scoped access represents a paradigm shift in how organizations manage permissions for AI agents. By implementing scoped access, organizations can restrict AI agents to specific datasets and predefined actions, thereby creating a protective boundary around database interactions. This mechanism not only reduces the attack surface but also ensures that AI agents can perform their functions without exposing sensitive information or compromising data integrity.

### Introducing Synapsor Runner: The Architecture Behind Scoped Access

Synapsor Runner is a pivotal tool designed to facilitate scoped access in AI-agent interactions with databases. This Apache-2.0 runtime acts as an intermediary between a Model Client Protocol (MCP) client and relational databases like PostgreSQL and MySQL. Unlike traditional systems that expose raw SQL execution capabilities, Synapsor Runner provides a set of reviewed semantic capabilities, such as `billing.inspect_invoice` and `support.propose_plan_credit`. This controlled environment significantly enhances security by restricting the actions that AI agents can perform.

### Mechanisms of Scoped Access: Enforcing Boundaries

The architecture of Synapsor Runner enforces strict boundaries around the capabilities of AI agents through well-defined contracts. These contracts specify allowed actions, tenant scopes, and data access limits, ensuring that AI agents interact only with the data necessary for their tasks. For instance, a contract may allow an AI agent to read specific columns and rows while disallowing any write operations. This design principle is crucial for maintaining data integrity and security within AI workflows.

### Semantic Capabilities: Simplifying Interactions and Reducing Risks

The semantic capabilities provided by Synapsor Runner are central to its security model. By abstracting database interactions into high-level functions, organizations can limit the complexity that AI agents must handle. Instead of allowing arbitrary SQL queries, AI agents can propose changes through predefined functions. This approach not only simplifies interactions but also mitigates the risk of prompt injection attacks, as the agents cannot generate harmful SQL queries.

### Examining Prompt Injection: Risks and Limitations

Despite the advantages of scoped access, prompt injection remains a critical security concern. Prompt injection occurs when an attacker manipulates the input to an AI agent to execute unintended commands. While Synapsor Runner’s architecture helps contain the impact of such attacks by ensuring that even if an AI agent is tricked into attempting unauthorized actions, it lacks the necessary tools to execute those actions, it does not completely eliminate the threat. For example, if an agent is prompted to access data outside its allowed scope, the enforced boundaries prevent it from succeeding, thus protecting sensitive information. However, sophisticated attackers may still exploit weaknesses in input handling or semantic capabilities, potentially leading to unintended outcomes. 

To address these risks, organizations should implement robust input validation mechanisms, such as whitelisting acceptable input formats and employing machine learning models to identify anomalous input patterns. Regular updates and security patches for the Synapsor Runner can also help mitigate vulnerabilities that may be exploited through prompt injection. Additionally, conducting red team exercises can expose potential weaknesses in the system, allowing organizations to strengthen their defenses against such attacks.

### Real-World Applications of Scoped Access: Case Studies

Organizations across various sectors can derive significant benefits from implementing scoped access through tools like Synapsor Runner. In the finance sector, AI agents can analyze customer invoices without exposing sensitive financial data. By defining contracts that limit data access to only what is necessary for analysis, organizations can leverage AI capabilities while safeguarding critical information. Similarly, in customer support, AI agents can propose solutions based on limited customer data, ensuring compliance with data protection regulations.

### Case Study: E-Commerce Platform Enhancements

A leading e-commerce platform successfully integrated scoped access for its AI-driven customer support system. By restricting the AI agent’s access to only relevant customer data, the platform improved response accuracy and significantly reduced the risk of data breaches. In another scenario, a financial institution utilized scoped access to allow AI agents to propose credit adjustments without exposing sensitive account information, resulting in improved operational efficiency and enhanced security. These case studies highlight the tangible benefits of implementing scoped access in real-world applications.

### Best Practices for Implementing Scoped Access

To maximize the benefits of scoped access, organizations should adhere to best practices when implementing tools like Synapsor Runner. First, it is essential to clearly define the contracts governing AI agent interactions, specifying allowed actions, data access limits, and approval processes for sensitive operations. Second, organizations should regularly review and update these contracts to adapt to evolving business needs and security landscapes. Third, consider implementing tiered approval processes for high-risk operations to ensure human oversight is maintained where necessary. Fourth, organizations should conduct regular security audits to identify potential vulnerabilities in the scoped access implementation. Finally, monitoring AI agent activities can help identify potential security issues and refine access controls accordingly.

### Future Considerations for AI Security: Evolving Threats

As AI technologies continue to evolve, the importance of robust security measures will only increase. Organizations must remain vigilant in their approach to AI security, continuously assessing the effectiveness of scoped access and other protective measures. The landscape of AI and database interactions is dynamic, and as new threats emerge, so too must our strategies for safeguarding sensitive information. By adopting tools like Synapsor Runner and embracing the principles of scoped access, organizations can navigate this complex terrain more securely and efficiently.

### Conclusion: A Secure Path Forward for AI Integration

In summary, the integration of AI agents with databases presents unique security challenges that necessitate innovative solutions. Scoped access, as exemplified by Synapsor Runner, offers a promising approach to mitigating risks while enabling AI agents to perform their functions effectively. By implementing scoped access, organizations can enhance their security posture, protect sensitive data, and maintain operational efficiency. However, it is crucial to remain aware of its limitations, particularly concerning prompt injection. Organizations must adopt a comprehensive security strategy that includes continuous monitoring, input validation, and adaptation to evolving threats, ensuring that the benefits of scoped access are fully realized.
