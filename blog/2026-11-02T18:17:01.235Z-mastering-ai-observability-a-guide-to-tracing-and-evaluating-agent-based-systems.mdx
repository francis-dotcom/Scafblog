Traditional backend observability is built around relatively predictable execution paths.
A request enters an application, passes through several services, interacts with a database, and eventually returns a response. We can use logs, metrics, and distributed traces to understand what happened and where a problem occurred.
AI agents introduce a different level of complexity.
An agent does not necessarily follow a predefined execution path. It may call an LLM multiple times, select tools dynamically, retry failed operations, delegate tasks to other agents, retrieve external context, or wait for additional user input.
Consider a relatively simple task:
A user asks an AI assistant to analyze a merge request and identify potential problems.
Behind the scenes, the application might:
Receive the user's request.
Invoke a coordinator agent.
Call an LLM to determine the next action.
Retrieve the merge request from GitLab.
Read the changed files.
Delegate security analysis to another agent.
Execute additional tool calls.
Evaluate the collected results.
Generate a final report.
The user sees one response. The application has actually executed a multi-step workflow involving several components.
Now imagine the response takes 45 seconds instead of the expected 8 seconds.
Where should we investigate?
Did the model take too long to respond?
Did a tool call time out?
Was the same operation executed repeatedly?
Did the agent generate unnecessary steps?
Did a subagent introduce additional latency?
Was too much context sent to the model?
Did a retry increase the overall execution time and cost?
Traditional request-level logging may tell us that the endpoint took 45 seconds. It does not necessarily explain why.
AI observability is about understanding the entire execution path, not just measuring the final API response.
This is where OpenTelemetry becomes particularly useful.
** is an open-source observability framework for collecting, processing, and exporting telemetry data.
It provides a vendor-neutral instrumentation model that allows applications to generate telemetry and send it to different observability platforms.
Instead of implementing a separate monitoring integration for every vendor, we can instrument an application using OpenTelemetry and choose where the telemetry should be exported.
OpenTelemetry is built around three primary signals:



Signal
What it tells us
AI agent example




Traces
How an operation was executed
Model call → tool → subagent


Metrics
How the system performs over time
Token usage, latency, error rate


Logs

Tool timeout or agent exception



These signals complement each other.
A metric can tell us that the average execution time has increased. A trace can identify which operation introduced the delay. A log can provide the error details associated with that operation.
OpenTelemetry also provides context propagation, APIs, SDKs, semantic conventions, and the OpenTelemetry Collector.
An important implementation detail: as of November 2026, the OpenTelemetry JavaScript documentation lists traces and metrics as Stable, while logs remain in Development. The maturity of a specific GenAI convention should also be evaluated separately from the maturity of the underlying OTel signal.

Before discussing AI-specific instrumentation, we need to understand traces and spans.
A trace represents the complete execution path of an operation.
A span represents one individual unit of work within that execution.
For example:
Trace: POST /api/agent
|
+-- HTTP Request
    |
    +-- Coordinator Agent
        |
        +-- LLM Generation
        |
        +-- Tool: GitLab - Get Merge Request
        |
        +-- Tool: GitLab - Get Changed Files
        |
        +-- Security Agent
        |   |
        |   +-- LLM Generation
        |   |
        |   +-- Tool: Security Analysis
        |
        +-- Testing Agent
        |   |
        |   +-- LLM Generation
        |   |
        |   +-- Tool: Test Coverage
        |
        +-- Final Response Generation

Each span has information such as:
Trace ID
Span ID
Parent span ID
Start and end timestamps
Duration
Attributes
Events
Status and exception information
This creates a hierarchical representation of the complete execution.
The key benefit is that we can move from a high-level workflow to an individual model call or tool execution without losing the relationship between them.
For AI agents, this distinction is important because one user request can generate many independent operations.
In distributed systems, a trace often crosses multiple services.
Imagine a Next.js application calling a .NET backend, which then delegates a task to a Python agent and receives a result from another service.
Without context propagation, every service may generate its own independent trace.
We would see several unrelated operations instead of one complete workflow.
OpenTelemetry uses W3C Trace Context as its standard propagation format. The traceparent header carries trace and parent-span information between instrumented services.
The same principle applies to agent-based architectures.
When an agent delegates a task to another agent through A2A, we should preserve the correlation between the originating request and the remote execution.
Automatic HTTP instrumentation can handle propagation when the HTTP instrumentation and context manager are configured correctly. Custom transports and asynchronous message queues may require explicit context injection and extraction.
The important point is that protocol-level interoperability and observability context propagation are separate concerns. Using A2A does not, by itself, guarantee that all distributed spans will appear in one trace.

One of the challenges in AI observability is the lack of consistent naming and structure across different AI frameworks and providers.
For example, one framework might represent an LLM request as a generic operation, while another might expose model-specific attributes.
This makes it difficult to compare different implementations using the same monitoring platform.
OpenTelemetry addresses this through Semantic Conventions.
Semantic conventions define common attribute names, operation types, and instrumentation expectations so that telemetry from different implementations can be interpreted consistently.

Since many TypeScript applications use the Vercel AI SDK to implement model interactions and agent workflows, it is worth looking at its native telemetry integration.
The AI SDK already supports OpenTelemetry-based instrumentation.
It can generate spans for:

Agent execution

This means we do not need to manually instrument every model call and tool execution just to obtain basic execution visibility.
For an AI SDK v7 application:
pnpm add @ai-sdk/otel @vercel/otel

The OpenTelemetry integration is provided through @ai-sdk/otel.
This is an important version-specific detail.
In AI SDK v7, OpenTelemetry integration moved out of the core ai package. Older examples using the v6 experimental_telemetry configuration should not be copied directly into a v7 application.
Create an instrumentation.ts file in the project root.
import { registerOTel } from '@vercel/otel';
import { registerTelemetry } from 'ai';
import { OpenTelemetry } from '@ai-sdk/otel';

export function register() {
  registerOTel({
    serviceName: 'ai-agent-platform',
  });

  registerTelemetry(
    new OpenTelemetry({
      recordInputs: false,
      recordOutputs: false,
    }),
  );
}

There are two responsibilities here:
registerOTel initializes the OpenTelemetry infrastructure for the Next.js application.
registerTelemetry registers the AI SDK-specific integration that creates GenAI spans.
I have disabled input and output capture in this example intentionally.
AI SDK telemetry can record prompts and generated outputs by default. In an enterprise environment, capturing this data requires an explicit privacy and security decision.
We will return to this in the security section.
For a regular Node.js application without Next.js, register the OpenTelemetry integration once at application startup.
Once telemetry is registered, supported AI SDK operations automatically emit telemetry through the registered integration.
We can also provide a functionId to identify the business operation or agent.
import { generateText } from 'ai';

const result = await generateText({

The functionId helps distinguish operations in traces.
For example, rather than seeing only generic model invocation spans, we can identify a specific business operation such as:

The AI SDK v7 OpenTelemetry integration follows the GenAI semantic conventions.
For generateText and streamText, the integration records three main types of spans:
1. Agent invocation span
The root span represents the complete generation operation, including its execution steps and tool calls.
Example:
invoke_agent portfolio-analysis-agent

2. Step and model-call spans
Each model interaction is represented by step and provider-call spans.
These allow us to understand how many model calls occurred during an operation and how long each one took.
3. Tool execution spans
Each client-side tool execution receives its own span.
For example:
invoke_agent portfolio-analysis-agent
|
+-- step 0
|   |
|   +-- chat example-model
|   +-- execute_tool get_portfolio
|
+-- step 1
|   |
|   +-- chat example-model
|   +-- execute_tool get_market_data
|
+-- step 2
    |
    +-- chat example-model

The resulting trace provides a much more complete representation of an agent workflow than a single model request log.
The integration also records usage information such as input tokens, output tokens, cache usage, model identifiers, and operation duration when these values are available.
Sometimes the standard GenAI attributes are not enough.
For example, we may want to know which business workflow initiated an operation or which application component owns it.
The AI SDK provides enrichSpan for adding custom attributes:
import { registerTelemetry } from 'ai';
import { OpenTelemetry } from '@ai-sdk/otel';

registerTelemetry(
  new OpenTelemetry({
    recordInputs: false,
    recordOutputs: false,

    enrichSpan: ({ spanType, operationId }) => ({
      'app.component': 'portfolio-assistant',
      'app.operation_id': operationId,
      'app.span_type': spanType,
    }),
  }),
);

The exact context available to enrichSpan depends on the span and the SDK's integration API.
The objective is to enrich the trace with useful application-level context without copying sensitive business data into telemetry.

Built-in instrumentation is useful, but it does not automatically understand every application-level decision.
For example, an AI SDK trace may show model calls and tool executions, but it may not tell us why a coordinator selected a particular specialist agent or how long a business workflow spent waiting for an approval.
These are application-level operations.
We should instrument them explicitly.
OpenTelemetry provides a tracing API for creating custom spans.
Consider a custom agent orchestration function:
import {
  trace,
  SpanStatusCode,
} from '@opentelemetry/api';

const tracer = trace.getTracer('agent-orchestrator');

export async function runReviewWorkflow() {
  return tracer.startActiveSpan(
    'workflow.merge-request-review',
    async (span) => {
      span.setAttribute(
        'workflow.name',
        'merge-request-review',
      );

      span.setAttribute(
        'workflow.version',
        '1.0.0',
      );

      try {
        const result = await executeReview();

        span.setStatus({
          code: SpanStatusCode.OK,
        });

        return result;
      } catch (cause) {
        const error =
          cause instanceof Error
            ? cause
            : new Error(String(cause));

        span.recordException(error);

        span.setStatus({
          code: SpanStatusCode.ERROR,
        });

        throw error;
      } finally {
        span.end();
      }
    },
  );
}

Any supported AI SDK operations executed inside this active span can become child operations in the same trace, provided the OpenTelemetry context is correctly propagated.

Framework-level instrumentation describes model and tool execution.
Application-level instrumentation describes business workflows and orchestration decisions.
This distinction is important.
We should not expect a model instrumentation library to understand the complete business meaning of an application request.
For A2A-based systems, distributed tracing becomes even more important.

This distinction is worth emphasizing.
Observability tells us what happened during execution.
Evaluation tells us whether the result was good enough.
A trace can show that an agent:
Called the correct model.
Used three tools.
Retrieved five documents.
Completed within four seconds.
Returned a response without an exception.
But none of these facts proves that the answer was correct.
Consider a RAG application.
The retrieval operation may complete successfully, and the model may return a fluent answer. However, the retrieved documents may be irrelevant or the final answer may contain unsupported information.
From an operational perspective, the request succeeded.
From a quality perspective, it failed.
We need both observability and evaluation.
Offline evaluation measures an AI application against a predefined dataset.
For example, we can create 100 representative questions and expected outcomes.
Whenever we modify a prompt, model, retrieval strategy, or agent workflow, we run the same dataset again.
This helps identify regressions before deploying changes.
Useful evaluation dimensions include:
Answer correctness
Relevance
Groundedness
Tool selection
Expected task completion
Policy compliance
Online evaluation measures actual production interactions.
We can select a sample of production traces and evaluate them using:
Rule-based checks
Code-based evaluators
LLM-as-a-Judge
Human feedback
The important part is to turn real production failures into future test cases.
For example:
A production trace shows that an agent selected the wrong tool.
We identify the relevant input and expected behavior.
We create a regression dataset entry.
We update the prompt or agent implementation.
We rerun offline evaluations.
We deploy and monitor the next set of production traces.

Agent-based workflows can generate a significant amount of telemetry.
Consider an agent that performs 15 model calls and 20 tool calls during a single task.
If the application handles thousands of tasks per hour, storing every span indefinitely may become expensive.
Sampling helps control this volume.
There are two common approaches.
The sampling decision is made when the trace starts.
For example, we may decide to sample 10% of incoming requests.
This is relatively simple and reduces the amount of telemetry generated or exported.
However, we do not yet know whether a trace will eventually fail or become unusually slow.
The sampling decision is made after considering the trace's collected spans.
This makes it possible to retain:
All failed traces.
All traces exceeding a latency threshold.
Traces containing specific tool failures.
A percentage of successful traces.
For AI agents, tail-based sampling can be particularly useful because many execution problems only become visible after several operations have completed.
However, tail sampling has an important infrastructure requirement: all spans belonging to the same trace must reach the same tail-sampling Collector instance.
This generally requires trace-ID-aware routing when using multiple Collector instances.
A practical approach is to combine sampling strategies:
Preserve error and high-latency traces.
Retain a representative sample of successful traces.
Maintain complete aggregate metrics where possible.
Apply stricter retention policies to verbose telemetry.

OpenTelemetry provides a strong foundation, but it is not a complete AI observability solution by itself.
Not every framework, provider, or agent runtime exposes the same information.
Some integrations can automatically trace model calls and tool execution, while others require custom instrumentation.
We should verify what is actually captured rather than assuming that installing an OpenTelemetry package provides complete visibility.
The GenAI conventions are still under development.
Attribute names, operation models, and implementation support may evolve.
Teams should pin versions, review changes, and avoid coupling application business logic to conventions that have not reached the required maturity.
A trace can explain what happened but does not prove that the model's result is correct.
Evaluation datasets, deterministic checks, and human feedback remain necessary.
Collecting every input, output, tool argument, and execution event can generate significant storage and processing overhead.
We should measure the cost of observability itself.
Adding unique user IDs, conversation IDs, trace IDs, or request IDs to metric labels can create an excessive number of time series.
Use traces for request-level correlation and keep metric dimensions bounded.
A2A communication, queues, background tasks, and remote tool execution may cross process boundaries.
If context is lost, we can end up with disconnected traces.
LLM-as-a-Judge can provide useful signals, but it can also be inconsistent or biased.
A single evaluation score should not become the only definition of quality.
Combine deterministic checks, representative datasets, human review, and calibrated evaluators.

### The Unique Challenges of AI Agent Execution

AI agents operate in a fundamentally different paradigm compared to traditional backend systems. While conventional applications follow linear execution paths, AI agents often engage in dynamic workflows that adapt based on user inputs, external contexts, and model interactions. For instance, when a user requests a code review, the AI agent may invoke a series of models, delegate tasks to sub-agents, and interact with various APIs. This complexity creates a multifaceted execution landscape where performance bottlenecks can arise from numerous sources, such as model latency, tool timeouts, and inefficient orchestration. Understanding these intricate execution paths is essential for effective monitoring and optimization. 

A practical example of this complexity can be seen in a chatbot system where user queries lead to different processing paths based on the context. For instance, a simple greeting may require minimal processing, whereas a request for technical support could trigger a cascade of model invocations, including natural language understanding, intent recognition, and retrieval of relevant knowledge from a database.

### The Role of OpenTelemetry in AI Observability

OpenTelemetry serves as a pivotal framework for enhancing observability in AI systems. It provides a vendor-neutral approach to collecting, processing, and exporting telemetry data, allowing developers to instrument their applications without being tied to a specific observability platform. This flexibility is particularly crucial for AI applications, where comprehensive insights into execution paths are necessary for effective monitoring and optimization. By leveraging OpenTelemetry, teams can generate a rich tapestry of traces, metrics, and logs that illuminate the complex interactions within AI workflows, facilitating both performance analysis and cost management.

For example, an AI-driven recommendation engine can utilize OpenTelemetry to trace the flow of data from user interactions through various models, capturing the time taken at each stage and identifying any delays that may affect user experience.

### Understanding Traces, Metrics, and Logs in AI Systems

In the context of AI observability, traces, metrics, and logs play distinct yet interconnected roles. Traces provide a detailed view of how operations are executed, revealing the sequence of model calls and tool executions. For example, tracing the execution of a code review request could highlight each step taken by the coordinator agent, from invoking a language model (LLM) to generating the final report. Metrics quantify system performance over time, capturing data such as average latency and error rates, while logs document specific events or exceptions encountered during execution. This triad of observability signals empowers teams to diagnose issues comprehensively and make informed decisions to enhance system performance.

To illustrate, consider a scenario where an AI agent processes a user query. The trace might show the invocation of multiple models, each contributing to the final output. Metrics could reveal that one model consistently exceeds latency thresholds, while logs might capture an error that occurred during a specific invocation, leading to a deeper investigation.

### Semantic Conventions: Standardizing Observability Across AI Frameworks

A significant challenge in AI observability is the inconsistency in naming conventions across various frameworks and models. OpenTelemetry addresses this by introducing semantic conventions that define common attributes and operation types. For instance, when logging an LLM invocation, attributes like `gen_ai.provider.name`, `gen_ai.request.model`, and `gen_ai.usage.input_tokens` can be employed to maintain consistency across different implementations. This standardization simplifies monitoring and enables comparative analysis across diverse AI systems, allowing teams to identify best practices and optimize performance effectively.

For example, when comparing the performance of different LLMs, using standardized attributes allows teams to aggregate data across systems and identify which model performs best under specific conditions, enhancing decision-making processes.

### The Importance of Custom Instrumentation in AI Workflows

While built-in instrumentation provides a solid foundation, custom instrumentation is often essential to capture application-specific nuances. For example, an AI agent's orchestration function may require explicit spans to track decision-making processes not covered by standard telemetry. By creating custom spans, developers can gain insights into why certain agents were selected for specific tasks or how long workflows spent waiting for approvals. This level of detail is crucial for diagnosing issues arising from complex agent interactions and ensuring optimal performance.

In a practical scenario, if an AI agent is designed to prioritize certain tasks based on user history, custom spans can help track the logic behind these decisions, providing clarity on how effectively the agent is meeting user needs.

### Evaluating AI Performance: Key Metrics to Monitor

To effectively evaluate the performance of AI agents, it is vital to identify and track relevant metrics. Key performance indicators (KPIs) may include end-to-end workflow duration, model request latency, and tool execution times. For instance, measuring the time to the first token can yield insights into perceived response latency, which is crucial for user experience. Additionally, tracking success rates for agent executions and tool calls can help pinpoint areas for improvement. By focusing on these metrics, teams can ensure that their AI systems not only function correctly but also meet user expectations regarding speed and reliability.

For example, in a customer support AI system, monitoring the average time taken to resolve queries can help identify bottlenecks, allowing teams to adjust workflows or enhance model training to improve response times.

### Cost Attribution: Understanding the Financial Impact of AI Workflows

As AI systems grow in complexity, grasping the financial implications of their operations becomes essential. Cost attribution involves analyzing resource consumption across various components of an AI workflow, such as model inference, embedding generation, and external API calls. For example, the total cost of a workflow can be represented mathematically as:

$$
C_{\text{workflow}} = \sum_{i} C_{\text{model}}(T_i) + C_{\text{external}}(E_j)
$$

where \(C_{\text{model}}\) represents the cost associated with model operations and \(C_{\text{external}}\) accounts for external service calls. This comprehensive view of costs enables organizations to make informed decisions about resource allocation and optimization strategies, ultimately leading to more efficient AI systems.

In practice, an organization might discover that a particular model is disproportionately driving costs due to high latency and frequent retries, prompting a review of the model's architecture or the introduction of caching mechanisms to mitigate expenses.

### Security and Privacy Considerations in Telemetry

The collection and storage of telemetry data in AI systems raise significant security and privacy concerns. Sensitive information, such as user prompts and model outputs, can inadvertently be exposed if not managed properly. For instance, OpenTelemetry's default behavior is to record inputs and outputs, which may not be suitable for all production environments. Organizations should implement strict policies regarding data retention, access controls, and anonymization to mitigate risks. Strategies such as data masking, encryption of sensitive fields, and limiting access to telemetry data based on roles can further enhance security. By prioritizing security in their observability practices, teams can ensure that they maintain user trust while still gaining valuable insights into system performance.

A concrete example includes implementing a policy where personally identifiable information (PII) is masked before being logged, ensuring compliance with data protection regulations while still allowing for effective monitoring.

### The Interplay Between Observability and Evaluation

Observability and evaluation are interdependent processes that must work in concert to foster continuous improvement in AI systems. While observability provides insights into execution events, evaluation assesses whether the outcomes meet predefined standards. For example, an AI agent may successfully complete a task but still fail to meet quality benchmarks. Implementing a feedback loop that incorporates production traces into evaluation datasets allows teams to identify regressions and refine their models and workflows accordingly. This iterative process is vital for enhancing the overall effectiveness of AI applications.

For instance, if an AI model consistently underperforms in specific scenarios, the observability data can help pinpoint the issue, leading to targeted improvements in the model's training data or architecture.

### Case Study: Observability in a Multi-Agent System

Consider a scenario where a multi-agent system is employed to analyze merge requests in a code repository. The system comprises a coordinator agent that delegates tasks to security and testing agents, each responsible for specific analyses. By implementing OpenTelemetry, the organization can trace the entire workflow from the initial user request to the final report generation. Each agent's performance can be monitored through metrics such as execution duration and success rates, while logs capture any exceptions or errors encountered during the process. This comprehensive observability framework enables the organization to identify bottlenecks, optimize agent interactions, and ultimately improve the system's responsiveness and accuracy.

In this case, the organization might find that the security agent frequently encounters errors due to outdated dependencies, prompting a review of the agent's environment and leading to improved stability and performance.

### Establishing a Robust Observability Framework

To build a robust observability framework for AI agents, organizations should adopt a phased approach. Initial phases should focus on establishing basic telemetry and standardizing semantic conventions, followed by integrating advanced observability techniques such as custom instrumentation and cost attribution. Continuous monitoring and evaluation should be embedded into the development lifecycle to ensure that observability remains a priority throughout the software development process. By fostering a culture of observability, organizations can enhance their AI systems' performance, reliability, and overall value.

### Conclusion: The Imperative of AI Observability

As AI systems continue to evolve, the demand for advanced observability techniques will only increase. By leveraging frameworks like OpenTelemetry and establishing standardized practices, organizations can gain deeper insights into the performance of their AI agents. This understanding will facilitate optimization efforts and enhance decision-making processes regarding resource allocation and cost management. Ultimately, the ability to effectively monitor and evaluate AI systems will be a critical differentiator for organizations seeking to harness the full potential of artificial intelligence, ensuring they remain competitive in a rapidly changing landscape.
