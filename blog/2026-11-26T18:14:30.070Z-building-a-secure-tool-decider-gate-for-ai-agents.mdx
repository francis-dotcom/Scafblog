An AI agent can produce a perfectly plausible tool call that your runtime happily executes: a SQL statement against the wrong table, a shell command with an unexpected flag, a payment request for the wrong amount. The model was not "lying" in a moral sense; it was optimizing for a plausible next step, and plausibility is not correctness.
The fix is to move authorization and policy decisions out of the model's discretion and into a deterministic layer that sits between the agent and every side-effecting tool. This layer is often called a tool-decider gate. It parses structured tool calls, evaluates them against explicit, testable rules, and either returns an execution plan, a correction request, or a hard denial.
This tutorial builds that gate for a real agent workflow using TypeScript, Zod, and a small policy engine. The result is not merely a safer agent; it is an auditable one, where every decision has a machine-readable reason code and a replayable evidence trail.

Most agent frameworks assume the model emits a tool call and the runtime executes it. That assumption is fine for read-only tools with no sensitive parameters. It breaks down when a tool can mutate state, spend money, delete data, or reach an internal network.
Consider a customer-support agent asked to "refund order A-1042 for $49.00." A model might emit:
{
  "tool": "issue_refund",
  "args": {
    "orderId": "A-1042",
    "amount": 4900,
    "currency": "USD",
    "reason": "customer_request"
  }
}

That looks correct. Now consider the same agent under a slightly different prompt, where the model confuses cents and dollars:
{
  "tool": "issue_refund",
  "args": {
    "orderId": "A-1042",
    "amount": 49,
    "currency": "USD",
    "reason": "customer_request"
  }
}

The second call is structurally valid, semantically wrong, and will happily refund $0.49 while reporting $49.00 to the customer. No schema validator catches this. No prompt makes it reliably safe.
The general failure mode is that language models are probabilistic generators of text-shaped actions, while production systems require deterministic acceptance criteria over structured actions. The gap between the two is where bluffs become incidents.
A tool-decider gate narrows that gap by enforcing four properties:
Type validity — the call matches a declared tool schema.
Contextual validity — the call satisfies constraints derived from the current task, session, and environment.
Authority validity — the call is permitted for this agent, this user, and this step.
Evidence validity — the call references facts that the system can independently verify, not facts the model asserted.
The gate must be ordinary code. It must never ask a model whether it thinks the call is safe.
The gate is a chokepoint. Every tool call, whether generated by a model, a planner, a sub-agent, or a human-facing UI, passes through it.

Two design rules follow immediately.
The gate returns decisions, not just booleans. A boolean false tells the agent nothing useful. A structured denial tells it exactly which field failed, what constraint applies, and what it must do next. That distinction is what turns a gate from a wall into a feedback loop.
The executor trusts only the gate's output. The executor should never re-derive policy, and the model should never be able to construct an execution plan directly. If the agent can bypass the gate, the gate is decoration.
A useful mental model: the LLM is a proposal engine, and the gate is the compiler front end. The model's output is untrusted source code. The gate performs type checking, semantic analysis, and admission control before anything runs.

Note the schema details that do real work. amount is an integer in minor units, so decimal-cent ambiguity disappears at the type level. orderId has a format constraint, which rejects a hallucinated identifier before it reaches the database. limit is capped, which prevents a model from requesting an unbounded scan.
The effect field classifies risk. requiresHumanApproval marks tools where the gate must find a valid approval token. These are not prompts; they are control-flow branches.
The decider takes a proposed call plus context and returns a decision. It must be a pure function of its inputs, apart from explicitly injected lookups.
Create src/gate/decider.ts:
import { z } from "zod";
import { toolRegistry, type ExecutionContext, type ToolName } from "../tools/registry.js";
import { evaluateRules, type RuleResult } from "../policy/rules.js";

export type Decision =
  | {
      status: "allow";
      tool: ToolName;
      args: Record<string, unknown>;
      /** Rule IDs that explicitly permitted this action. */
      satisfiedBy: string[];
      /** Facts the executor may rely on. */
      evidence: Record<string, unknown>;
    }
  | {
      status: "repair";
      tool: ToolName;
      reasonCode: string;
      message: string;
      /** Machine-readable hints the agent can act on. */
      violations: RuleResult[];
    }
  | {
      status: "deny";
      tool: ToolName | "unknown";
      reasonCode: string;
      message: string;
      violations: RuleResult[];
    };

export interface ProposedCall {
  tool: string;
  args: unknown;
}

export interface DeciderDeps {
  /** Resolves facts independently of the model. */
  lookupFacts: (ctx: ExecutionContext) => Promise<Record<string, unknown>>;
  /** Verifies an approval token. Inject a real verifier in production. */
  verifyApproval: (token: string, ctx: ExecutionContext) => Promise<boolean>;
}

const KNOWN_TOOLS = new Set<string>(Object.keys(toolRegistry));

export async function decide(
  proposed: ProposedCall,
  ctx: ExecutionContext,
  deps: DeciderDeps,
): Promise<Decision> {
  // Step 1: is this even a tool we know about?
  if (!KNOWN_TOOLS.has(proposed.tool)) {
    return {
      status: "deny",
      tool: "unknown",
      reasonCode: "UNKNOWN_TOOL",
      message: `Tool "${proposed.tool}" is not registered. Available tools: ${[...KNOWN_TOOLS].join(", ")}.`,
      violations: [],
    };
  }

  const toolName = proposed.tool as ToolName;
  const tool = toolRegistry[toolName];

  // Step 2: structural validation. Never trust shape from the model.
  const parsed = tool.argsSchema.safeParse(proposed.args);
  if (!parsed.success) {
    const issues = parsed.error.issues.map((i) => ({
      ruleId: "SCHEMA_VALIDATION",
      field: i.path.join(".") || "<root>",
      message: i.message,
    }));

    return {
      status: "repair",
      tool: toolName,
      reasonCode: "SCHEMA_VIOLATION",
      message: "Tool arguments failed schema validation. Fix the fields listed and retry.",
      violations: issues,
    };
  }

  const args = parsed.data as Record<string, unknown>;

  // Step 3: gather independent facts. The model cannot supply these.
  const facts = { ...ctx.facts, ...(await deps.lookupFacts(ctx)) };

  // Step 4: deterministic policy evaluation.
  const results = await evaluateRules(toolName, args, { ...ctx, facts });
  const failures = results.filter((r) => r.status === "fail");

  if (failures.length > 0) {
    const hard = failures.filter((r) => r.severity === "hard");
    const soft = failures.filter((r) => r.severity === "soft");

    if (hard.length > 0) {
      return {
        status: "deny",
        tool: toolName,
        reasonCode: hard[0]!.ruleId,
        message: hard.map((h) => h.message).join(" "),
        violations: failures,
      };
    }

    return {
      status: "repair",
      tool: toolName,
      reasonCode: soft[0]!.ruleId,
      message: soft.map((s) => s.message).join(" "),
      violations: failures,
    };
  }

  // Step 5: approval requirement for high-risk effects.
  if (tool.requiresHumanApproval) {
    const token = ctx.approvalToken;\n    const approved = token ? await deps.verifyApproval(token, ctx) : false;
    if (!approved) {
      return {
        status: "deny",
        tool: toolName,
        reasonCode: "HUMAN_APPROVAL_REQUIRED",
        message:
          "This action requires human approval. Present the proposed action to an authorized approver and retry with a valid approval token.",
        violations: [
          {
            ruleId: "HUMAN_APPROVAL_REQUIRED",
            status: "fail",
            severity: "hard",
            field: "approvalToken",
            message: "No valid approval token was supplied for this action.",
          },
        ],
      };
    }
  }

  return {
    status: "allow",
    tool: toolName,
    args,
    satisfiedBy: results.filter((r) => r.status === "pass").map((r) => r.ruleId),
    evidence: facts,
  };
}

Three properties of this design matter more than the code itself.
Ordering is fixed. Unknown tool, then schema, then facts, then policy, then approval. Changing the order changes security semantics, so treat it as part of the contract.
Facts flow one way. The gate collects facts from trusted systems. Model-provided claims can be proposed as facts, but they are never promoted to facts by the gate.
Repair and deny are distinct. A schema error is repairable: the agent can retry with corrected fields. A policy violation like "refund exceeds order total" may also be repairable if the agent can look up the correct amount. But an unknown tool or a missing approval token is a deny. Conflating them causes agents to loop, retrying the same thing against a wall.
Rules are small, named, independently testable predicates. They receive the validated arguments, the execution context, and trusted facts.
Create src/policy/rules.ts:
import type { ExecutionContext, ToolName } from "../tools/registry.js";

export type RuleSeverity = "hard" | "soft";

exnexport interface RuleResult {
  ruleId: string;
  status: "pass" | "fail";
  severity: RuleSeverity;
  field?: string;
  message: string;
}

export interface RuleContext extends ExecutionContext {
  facts: Record<string, unknown>;
}

export type Rule = (
  args: Record<string, unknown>,
  ctx: RuleContext,
) => RuleResult | Promise<RuleResult>;

const pass = (ruleId: string, message = "Rule satisfied."): RuleResult => ({
  ruleId,
  status: "pass",
  severity: "hard",
  message,
});

const fail = (
  ruleId: string,
  message: string,
  severity: RuleSeverity = "hard",
  field?: string,
): RuleResult => ({ ruleId, status: "fail", severity, message, ...(field ? { field } : {}) });

const refundAmountWithinOrder: Rule = async (args, ctx) => {
  const orderId = String(args.orderId ?? "");
  const order = (ctx.facts.orders as Record<string, { total: number; currency: string }> | undefined)?.[orderId];

  if (!order) {
    return fail(
      "ORDER_MUST_EXIST",
      `Order ${orderId} was not found in the order system. Call search_orders first and use a verified order ID.`,
      "soft",
      "orderId",
    );
  }

  const amount = Number(args.amount);
  if (amount > order.total) {
    return fail(
      "REFUND_EXCEEDS_ORDER_TOTAL",
      `Refund of ${amount} minor units exceeds the order total of ${order.total} for ${orderId}.`,
      "soft",
      "amount",
    );
  }

  if (args.currency !== order.currency) {
    return fail(
      "CURRENCY_MISMATCH",
      `Order ${orderId} is denominated in ${order.currency}, not ${String(args.currency)}.`,
      "soft",
      "currency",
    );
  }

  return pass("REFUND_WITHIN_ORDER_TOTAL");
};

const refundNotAboveAgentLimit: Rule = (args, ctx) => {
  const limit = Number(ctx.facts.agentRefundLimit ?? 0);
  const amount = Number(args.amount ?? 0);

  if (limit <= 0) {
    return fail("NO_REFUND_AUTHORITY", "This agent role has no refund authority configured.");
  }

  if (amount > limit) {
    return fail(
      "REFUND_EXCEEDS_AGENT_LIMIT",
      `Refund of ${amount} exceeds this agent's limit of ${limit}. Escalate to a human operator.`,
    );
  }

  return pass("REFUND_WITHIN_AGENT_LIMIT");
};

const emailOnlyToCustomer: Rule = async (args, ctx) => {
  const customerEmail = ctx.facts.customerEmail;
  const to = String(args.to ?? "").toLowerCase();

  if (typeof customerEmail !== "string") {
    return fail("CUSTOMER_CONTEXT_MISSING", "No customer context is bound to this session.");
  }

  if (to !== customerEmail.toLowerCase()) {
    return fail(
      "EMAIL_RECIPIENT_NOT_VERIFIED",
      `Recipient ${to} does not match the verified customer address for this session.`,
      "soft",
      "to",
    );
  }

  return pass("EMAIL_RECIPIENT_VERIFIED");
};

const readOnlyToolIsSafe: Rule = (args, ctx) =>
  pass("READ_TOOL_ALLOWED", `Read tool permitted for agent role ${ctx.agentRole}.`);

const rulesByTool: Record<ToolName, Rule[]> = {
  issue_refund: [refundAmountWithinOrder, refundNotAboveAgentLimit],
  search_orders: [readOnlyToolIsSafe],
  send_email: [emailOnlyToCustomer],
};

export async function evaluateRules(
  tool: ToolName,
  args: Record<string, unknown>,
  ctx: RuleContext,
): Promise<RuleResult[]> {
  const rules = rulesByTool[tool] ?? [];
  const results: RuleResult[] = [];

  for (const rule of rules) {
    results.push(await rule(args, ctx));
  }

  return results;
}

A rule has a stable ruleId. That ID is what appears in the audit log, the denial reason, and the dashboard. When a support engineer asks "why was this refund blocked?", the answer is a rule ID, not a stack trace or a paraphrase of a prompt.
Rules also have severity. A soft failure means the agent can plausibly correct itself by gathering more information. A hard failure means escalation is required. Getting this distinction wrong is a common source of agent loops: a hard failure returned as a repair prompt invites the model to retry indefinitely.
Now wire the gate into an agent loop. The loop asks a planner for a proposed call, then hands that call to the gate. Only an allow decision reaches the executor.
Create src/gate/executor.ts:
import { toolRegistry, type ExecutionContext, type ToolName } from "../tools/registry.js";
import type { Decision } from "./decider.js";

export interface ExecutionResult {
  tool: ToolName;
  output: unknown;
  durationMs: number;
}

/**
 * The executor accepts ONLY gate-approved plans. There is no path from a
 * proposed call to execution that bypasses `decide`.
 */
export async function executeApproved(
  decision: Decision,
  ctx: ExecutionContext,
): Promise<ExecutionResult> {
  if (decision.status !== "allow") {
    throw new Error(
      `Refusing to execute a ${decision.status} decision. Only "allow" decisions may execute.`,
    );
  }

  const tool = toolRegistry[decision.tool];
  const started = Date.now();
  const output = await tool.execute(decision.args as never, ctx);

  return {
    tool: decision.tool,
    output,
    durationMs: Date.now() - started,
  };
}

Now the agent loop. Create src/agent-loop.ts:
import { decide, type Decision, type DeciderDeps, type ProposedCall } from "./gate/decider.js";
import { executeApproved } from "./gate/executor.js";
import { writeAuditRecord } from "./audit/log.js";
import type { ExecutionContext } from "./tools/registry.js";

export interface Planner {
  /** Produces the next proposed tool call, or null when the task is complete. */
  nextProposal: (history: Turn[]) => Promise<ProposedCall | null>;
}

export interface Turn {
  role: "proposal" | "decision" | "result";
  content: string;
}

export interface LoopResult {
  turns: Turn[];
  finalOutput?: string;
  stoppedBecause: "completed" | "max_steps" | "denied";
}

const MAX_STEPS = 8;

export async function runAgent(
  planner: Planner,
  ctx: ExecutionContext,
  deps: DeciderDeps,
): Promise<LoopResult> {
  const history: Turn[] = [];

  for (let step = 0; step < MAX_STEPS; step++) {
    const proposal = await planner.nextProposal(history);

    if (proposal === null) {
      const finalOutput = history.findLast((t) => t.role === "result")?.content ?? "";
      return { turns: history, finalOutput, stoppedBecause: "completed" };
    }

    history.push({
      role: "proposal",
      content: JSON.stringify(proposal),
    });

    const decision = await decide(proposal, ctx, deps);
    history.push({
      role: "decision",
      content: JSON.stringify(decision),
    });

    await writeAuditRecord({
      requestId: ctx.requestId,
      tool: decision.tool,
      decision,
      proposedArgs: proposal.args,
    });

    if (decision.status === "deny") {
      return { turns: history, stoppedBecause: "denied" };
    }

    if (decision.status === "repair") {
      // The agent sees the structured violation and may try again.
      continue;
    }

    const result = await executeApproved(decision, ctx);
    history.push({
      role: "result",
      content: JSON.stringify(result.output),
    });
  }

  return { turns: history, stoppedBecause: "max_steps" };
}

Note that the loop never interprets a denial as success. A denied action ends the run and surfaces an escalation, which is exactly what you want when an agent tries to issue a refund beyond its authority.
The difference between a good denial and a bad denial is the information content. A bad denial says "blocked." A good denial says what failed, why, and what to do next.
Create src/gate/repair-prompt.ts:
import type { Decision } from "./decider.js";

/**
 * Convert a repair decision into a compact, structured instruction for the planner.
 * The planner sees facts and constraints, not prose negotiation.
 */
export function buildRepairInstruction(decision: Decision): string {
  if (decision.status !== "repair") {
    throw new Error("buildRepairInstruction expects a repair decision.");
  }

  const lines = [
    `The proposed call to \`${decision.tool}\` was rejected by policy.`,
    `Reason code: ${decision.reasonCode}`,
    "",
    "Violations:",
  ];

  for (const v of decision.violations) {
    const field = v.field ? ` [field: ${v.field}]` : "";
    lines.push(`- ${v.ruleId}${field}: ${v.message}`);
  }

  lines.push(
    "",
    "Do not repeat the same call. Either gather the missing information with an allowed read tool, correct the flagged field, or escalate to a human operator.",
  );

  return lines.join("\n");
}

Two safeguards belong here.
Cap repairs per rule. Track how many times each ruleId has produced a repair in a session. After two or three attempts, escalate. Without this, a model can oscillate between two near-identical calls indefinitely.
Never let repair widen authority. A repair instruction must not grant the agent new capabilities. It may only request a different value, a read to obtain a verified value, or escalation.
A denial should also be a first-class outcome in your API, not an exception. Something like:
{
  "status": "denied",
  "reasonCode": "REFUND_EXCEEDS_AGENT_LIMIT",
  "message": "Refund of 50000 exceeds this agent's limit of 20000. Escalate to a human operator.",
  "escalationTicket": "esc_9f2a"
}

Returning a structured denial lets the surrounding application route the case, notify the right team, and keep the customer informed without pretending the task succeeded.
Auditability requires more than logging that something happened. It requires reconstructing why a decision was made, with the exact inputs, the exact rule outcomes, and a tamper-evident record.
Create src/audit/log.ts:
import { createHash } from "node:crypto";
import type { Decision } from "../gate/decider.js";

export interface AuditRecord {
  requestId: string;
  tool: string;
  decision: Decision;
  proposedArgs: unknown;
  timestamp: string;
  /** Hash of the previous record, forming a tamper-evident chain. */
  prevHash: string;
  /** Hash of this record's canonical contents. */
  hash: string;
}

const records: AuditRecord[] = [];

function canonicalize(value: unknown): string {
  if (value === null || typeof value !== "object") {
    return JSON.stringify(value) ?? "null";
  }
  if (Array.isArray(value)) {
    return `[${value.map(canonicalize).join(",")}]`;
  }
  const entries = Object.entries(value as Record<string, unknown>)
    .filter(([, v]) => v !== undefined)
    .sort(([a], [b]) => a.localeCompare(b));
  return `{${entries.map(([k, v]) => `${JSON.stringify(k)}:${canonicalize(v)}`).join(",")}}`;
}

export async function writeAuditRecord(input: {
  requestId: string;
  tool: string;
  decision: Decision;
  proposedArgs: unknown;
}): Promise<AuditRecord> {
  const prevHash = records.at(-1)?.hash ?? "GENESIS";
  const timestamp = new Date().toISOString();

  const body = {
    requestId: input.requestId,
    tool: input.tool,
    decision: input.decision,
    proposedArgs: input.proposedArgs,
    timestamp,
    prevHash,
  };

  const hash = createHash("sha256").update(canonicalize(body)).digest("hex");
  const record: AuditRecord = { ...body, hash };

  records.push(record);

  // In production: append to an append-only store (Postgres, S3 Object Lock,
  // or a dedicated ledger service) and ship to your SIEM.
  console.log(`[audit] ${record.requestId} ${record.tool} ${input.decision.status} ${hash.slice(0, 12)}`);

  return record;
}

export function getAuditRecords(): readonly AuditRecord[] {
  return records;
}

The hash chain gives you a property that plain logs do not: you can detect modification or deletion of historical records. Recompute the chain over the stored records and compare. If a hash does not match, the log has been altered.
For production, ship audit records to append-only storage and keep the decision record separate from the full tool arguments if arguments contain PII. Store a redacted or hashed representation of sensitive fields, plus a pointer to the encrypted original under your retention policy.

The gate works in the tutorial. Production requires more.
Wrap tool invocation in a single exported function that requires a valid allow decision. Do not export raw tool executors to agent code. If you use an MCP server or a plugin system, enforce the same gate server-side, because a client-side gate protects only against honest clients.
An approval token must be scoped to a hash of the tool, arguments, actor, and expiry. Approving "issue a refund for order A-1042" must not authorize a different amount. Verify the token signature, expiry, and subject on every use, and burn it after use so it cannot be replayed.
The schema requires an idempotencyKey. Enforce it at the executor and at the downstream API: a duplicate key with different arguments is a conflict and must fail loudly, not silently reuse the first result.
As rule count grows, move rules into a declarative format (Rego, Cedar, OPA, or a JSON/YAML rule file) and keep the gate's evaluation order fixed. The gate stays deterministic; only the rule definitions become configurable.
Record the policy version and tool schema version in each audit entry. Without them, you cannot explain why a call allowed in March was denied in June after a rule change.
Maintain a corpus of real agent failures. Each becomes a test asserting the gate blocks it. This turns production incidents into permanent regression protection, and it is the single highest-leverage practice in this whole architecture.
The gate adds latency to every tool call. Keep it fast: cache facts with short TTLs, avoid network calls inside individual rules, and batch lookups before rule evaluation. If a fact lookup is slow, the model will route around the gate by trying more calls, which is worse than the latency you were trying to avoid.
Rules that an LLM generates at runtime are not deterministic and not auditable in the sense you need. If you want model-assisted policy authoring, generate a proposal that a human reviews and promotes into a versioned rule file.
A tool-decider gate is one component of a broader control plane. For more on structuring agent systems and the tooling around them, see Tamiz's Insights. For practical API integration patterns, tamiz.pro is a useful reference.
Should the tool-decider gate be a model or a rules engine?
A rules engine. The entire point is that the decision does not depend on a stochastic model. If you use an LLM to evaluate policy, you have moved the bluff rather than removed it. Models may assist in authoring rules, but the runtime path must be deterministic.
How do I handle tools with many valid argument shapes?
Use discriminated unions in the schema and branch the rules on the discriminator. Keep each branch's rules small and independently testable. If a tool has more than a handful of materially different modes, split it into multiple tools; smaller tools produce smaller policy surfaces.
Does this replace prompt engineering and output-format constraints?
No. Structured output and clear tool descriptions still matter, because they reduce the number of invalid proposals the model generates. But they are efficiency measures. The gate is the correctness boundary. Even a perfectly formatted call can be semantically wrong, and only the gate catches that.
How do I avoid the agent getting stuck in repair loops?
Track repair attempts per ruleId within a session, cap them at two or three, and escalate to a human on exhaustion. Also make repair messages actionable: name the field, state the constraint, and suggest the next allowed action. A repair that only says "invalid" gives the model nothing to converge on.
What is the minimum viable version of this pattern?
Three pieces: a strict schema per tool, one rule that checks arguments against trusted facts, and an executor that refuses anything without an allow decision. That alone eliminates the most common class of agent bluffs. Add approval tokens and audit chaining next, then expand the rule set as you observe real failures...."

### The Pitfall of Plausibility in AI Actions

AI agents, especially those leveraging large language models (LLMs), often produce outputs that seem plausible but can lead to significant operational risks. This arises from the probabilistic nature of LLMs, which prioritize generating likely responses over ensuring correctness. For example, an AI tasked with processing a refund may generate a request that appears well-structured but misinterprets the monetary amount due to unit confusion. Such missteps can result in unintended consequences, highlighting the need for a more deterministic approach to action validation within AI systems.

### Understanding the Tool-Decider Gate

To address the risks associated with plausible yet incorrect actions, we introduce the concept of a tool-decider gate. This gate acts as a deterministic layer that scrutinizes structured tool calls from AI agents. By evaluating each call against a predefined set of rules and schemas, the gate ensures that only valid actions are executed. This separation between the proposal stage and execution enhances both security and reliability, acting as a critical checkpoint in the AI agent's workflow.

### Architectural Design of the Tool-Decider Gate

The architecture of the tool-decider gate is founded on four essential properties: type validity, contextual validity, authority validity, and evidence validity.

- **Type Validity** ensures that the proposed action conforms to a defined schema, effectively filtering out malformed requests. For example, if a refund request includes an invalid currency code, the gate would reject it based on type validity.

- **Contextual Validity** assesses whether the action aligns with the current task and environmental constraints, ensuring that it is appropriate for the given context. For instance, if the refund tool is invoked while the system is in a maintenance mode, the action would be denied.

- **Authority Validity** checks whether the agent has the necessary permissions to perform the proposed action, safeguarding against unauthorized operations. If an agent attempts to issue a refund without the required managerial approval, the gate would block the action.

- **Evidence Validity** guarantees that the action is based on verifiable facts rather than assumptions made by the model. For example, the gate would require evidence that the order exists and the refund amount is justified based on transaction records.

This structured approach transforms the gate into a critical chokepoint, where every action must pass through rigorous validation before execution.

### Implementing the Tool-Decider Gate with TypeScript and Zod

To construct the tool-decider gate, we can utilize TypeScript for type safety and Zod for schema validation. The initial step involves defining the tool contracts that specify the expected input types for each tool. For instance, consider the refund tool, which can be defined as follows:

```typescript
import { z } from "zod";

export const refundArgsSchema = z.object({
  orderId: z.string().regex(/^[A-Z]{1,3}-\d{4,10}$/, "Invalid order ID format"),
  amount: z.number().int().positive().max(100_000),
  currency: z.enum(["USD", "EUR", "GBP"]),
  reason: z.enum(["customer_request", "damaged_item", "duplicate_charge"]),
  idempotencyKey: z.string().min(8).max(128),
});

export type RefundArgs = z.infer<typeof refundArgsSchema>;
```

This schema enforces that the `amount` is always an integer, thereby eliminating ambiguity associated with decimal values. By establishing such schemas, we create a single source of truth that drives both validation and policy enforcement.

### Crafting Policy Rules for Validation

Once the schemas are defined, we can implement policy rules that validate proposed actions based on the current context and facts. These rules are small, named predicates that return structured results indicating whether a proposed action is allowed, requires correction, or is denied outright.

For example, a rule may check if the refund amount exceeds the order total:

```typescript
const refundAmountWithinOrder: Rule = async (args, ctx) => {
  const orderId = String(args.orderId ?? "");
  const order = ctx.facts.orders[orderId];

  if (!order) {
    return fail("ORDER_MUST_EXIST", `Order ${orderId} was not found.`, "soft", "orderId");
  }

  const amount = Number(args.amount);
  if (amount > order.total) {
    return fail("REFUND_EXCEEDS_ORDER_TOTAL", `Refund exceeds order total for ${orderId}.`, "soft", "amount");
  }

  return pass("REFUND_WITHIN_ORDER_TOTAL");
};
```

This policy rule plays a crucial role in ensuring that only valid refund requests are processed, thereby preventing erroneous actions from being executed. By implementing several such rules, we can create a robust framework that addresses various edge cases.

### Integrating the Gate into the AI Agent Workflow

Integrating the tool-decider gate into an AI agent's workflow requires routing all proposed actions through the gate before execution. This guarantees that every action is validated against the defined schemas and policies. The agent generates a proposed tool call, which is then passed to the gate for evaluation:

```typescript
const decision = await decide(proposedCall, context, dependencies);
```

If the decision permits the action, it proceeds to execution; if not, the agent receives structured feedback indicating the reason for denial or the necessary corrections. This feedback mechanism is essential for continuous improvement, as it allows the AI agent to learn from its mistakes.

### Testing and Auditing Decisions Made by the Gate

Testing the tool-decider gate is vital for ensuring its reliability and effectiveness. Each policy rule should be independently testable, allowing rapid validation of the gate's decision-making process. For instance, unit tests can simulate various scenarios to ensure that invalid requests are appropriately denied. 

Here’s an example of a unit test for the refund amount rule:

```typescript
describe('refundAmountWithinOrder', () => {
  it('should deny refund if amount exceeds order total', async () => {
    const args = { orderId: "ABC-1234", amount: 200, currency: "USD" };
    const ctx = { facts: { orders: { "ABC-1234": { total: 100 } } } };
    const result = await refundAmountWithinOrder(args, ctx);
    expect(result).toEqual(fail("REFUND_EXCEEDS_ORDER_TOTAL", expect.any(String), "soft", "amount"));
  });
});
```

### Best Practices for Sustaining the Tool-Decider Gate

To ensure the long-term effectiveness of the tool-decider gate, several best practices should be adhered to:

1. **Regularly Update Policy Rules**: As new scenarios arise, policy rules should be updated to reflect the current operational context, ensuring that the gate remains effective against emerging threats.

2. **Monitor Performance**: The gate introduces latency into the system. Monitoring its performance and optimizing the decision-making process is essential to prevent bottlenecks.

3. **Implement Feedback Loops**: Establish mechanisms for the agent to learn from denied actions and repairs. This can help refine the model's proposals over time, reducing the frequency of errors.

4. **Conduct Regular Security Audits**: Periodic audits of the gate's operation can help identify vulnerabilities and areas for improvement, ensuring that security remains a top priority.

The implementation revealed several challenges, particularly around ensuring that the agent's understanding of order totals matched the actual data stored in their systems. By integrating the tool-decider gate, the company was able to enforce strict validation rules, significantly reducing the number of erroneous refunds issued. The gate's ability to validate against real-time data improved operational efficiency and customer satisfaction.

The introduction of a tool-decider gate represents a significant advancement in the security of AI agents. The tool-decider gate stands as a pivotal innovation in the ongoing quest for AI safety and reliability.
