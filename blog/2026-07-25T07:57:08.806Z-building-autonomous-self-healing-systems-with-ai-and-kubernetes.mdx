I built OmniSRE to answer exactly that question. But the moment I gave my AI agent the keys to my Docker socket, I realized that an autonomous agent with unchecked infrastructure access is genuinely terrifying. One bad LLM response, one stale approval message—and it starts restarting production containers on its own.
I needed a kill switch. So I built one into Telegram.

I wanted a completely reproducible observability environment. Instead of manually wiring up ClickHouse and the OpenTelemetry Collector, I used SigNoz Foundry CLI to spin up the entire self-hosted stack in under 2 minutes.
Why self-hosted SigNoz over a managed cloud tool? Two reasons: full ClickHouse query access (critical for the agent to pull raw logs programmatically), and zero data egress costs. The agent's entire log-extraction pipeline depends on direct /api/v1/query_range access—which you only get with self-hosted.
First, define the deployment manifest:
# casting.yaml - SigNoz Foundry Deployment Specification
apiVersion: v1alpha1
kind: Installation
metadata:
  name: signoz
spec:
  deployment:
    mode: docker
    flavor: compose
  mcp:
    spec:
      enabled: true

Then deploy the entire stack with a single command:
# Install Foundry and cast the infrastructure stack
curl -fsSL https://signoz.io/foundry.sh | bash
export PATH="$HOME/.local/bin:$PATH"

foundryctl cast -f casting.yaml

Within moments, six isolated core containers are live:
Port 3301 — SigNoz UI & Query Engine
Port 4317/4318 — OTLP gRPC/HTTP ingestion endpoints
OmniSRE is designed with a strict multi-container isolation model. Telemetry flows upstream into SigNoz. Remediation commands flow downstream via host-level socket bindings. The SRE Agent is completely decoupled from the application it monitors.

Key Design Principle: If buggy_service crashes and burns, omnisre_agent stays alive to fix it. They share zero runtime dependencies.
Here is the critical docker-compose.yml section showing the socket mount:
# config/docker-compose.yml

      - SIGNOZ_ENDPOINT=http://host.docker.internal:3301

To give the AI real, structured data to reason about, I instrumented the /checkout endpoint with OpenTelemetry SDKs and wired up explicit error span tagging. When chaos fires, the spans going into ClickHouse are not generic—they carry precise failure context.
# app/buggy_service.py
from fastapi import FastAPI, HTTPException
from opentelemetry import trace
from opentelemetry.trace import StatusCode

app = FastAPI(title="Buggy E-Commerce Checkout")
chaos_mode_enabled = False

@app.get("/checkout")
def checkout():
    global chaos_mode_enabled
    if chaos_mode_enabled:
        current_span = trace.get_current_span()
        if current_span.is_recording():
            current_span.set_status(StatusCode.ERROR, "Chaos mode active: Simulated 500 Outage")
            current_span.set_attribute("http.status_code", 500)

        raise HTTPException(status_code=500, detail="500 Internal Server Error: Connection pool exhausted.")
    return {"status": "success", "latency_ms": 25}

@app.post("/chaos/inject")
def inject_chaos():
    global chaos_mode_enabled
    chaos_mode_enabled = True
    return {"status": "chaos_injected", "message": "Simulated DB pool failure active."}

Webhook Channel: In SigNoz → Settings → Alert Channels, I configured a Webhook notification channel pointing to http://host.docker.internal:8001/webhook/signoz. The moment the alert fires, SigNoz POSTs a JSON payload directly to the SRE agent's receiver endpoint — no polling, no cron jobs.
This is the key integration point: SigNoz is not just a dashboard in this system. It is the event source that kicks off the entire autonomous remediation pipeline. Without the alert channel, nothing moves.
This was the hardest part of the entire build, and I guarantee you will hit this wall too.
Everything worked perfectly in my local Python environment. But the moment I containerized the agent, the observability pipeline went blind. The agent received the webhook, then crashed trying to query ClickHouse logs.
The error log: Connection Refused: localhost:3301
The Insight: localhost inside a Docker container is the container itself—not your host machine. SigNoz was running fine on host:3301, but the agent was knocking on its own door.
To fix this resiliently across any deployment environment, I built an automatic fallback engine:
# agent/investigator.py
import requests

class SigNozInvestigator:
    # Ordered priority matrix for cross-container bridge resolution
    FALLBACK_ENDPOINTS = [
        "http://localhost:3301",
        "http://host.docker.internal:3301",
        "http://signoz-frontend:3301"
    ]

    def fetch_real_signoz_logs(self, query_payload: dict) -> dict:
        for base_url in self.FALLBACK_ENDPOINTS:
            try:
                url = f"{base_url}/api/v1/query_range"
                response = requests.post(url, json=query_payload, timeout=3)
                if response.status_code == 200:
                    return response.json()
            except requests.exceptions.ConnectionError:
                continue
        raise ConnectionError("Failed to reach SigNoz ClickHouse backend across all bridges.")

The agent now auto-resolves the correct network bridge every single time. No manual configuration required.
SigNoz features used in this project: Distributed Tracing (Trace Explorer), ClickHouse Log Querying (/api/v1/query_range), Custom Metrics Dashboards (Query Builder), Threshold Alert Rules, and Webhook Alert Channels — five features running as one connected pipeline.

{

Why this prompt works: Forcing a strict JSON schema eliminates ambiguous, prose-based responses entirely. The agent's downstream healer.py can then deterministically parse action and target_service without any fragile string matching.
Having an AI that can diagnose a problem is amazing. Having an AI that can unilaterally modify .env files and execute container restarts is a recipe for a career-ending incident.
I needed a "Financial Kill Switch" for my infrastructure. So I built one into Telegram.
When SigNoz fires the alert, the pipeline executes like this:
SigNoz Alert → Webhook → Gemini RCA → Telegram HITL Gate → (YES) → Docker Heal
                                                          ↓
                                                     (NO / Timeout)
                                                          ↓
                                                  Abort. Log. Done.

The agent halts completely at the Telegram gate and sends a formatted diagnostic card showing exactly what it found and exactly what it plans to do. You reply YES or you walk away.
To prevent the agent from reading stale YES messages from previous incidents—a real bug I hit during testing that caused phantom auto-restarts—I implemented timestamp-filtered polling:
# agent/notifier.py
import time, requests

def wait_for_human_approval(bot_token: str, chat_id: str, alert_start_time: float) -> bool:
    """Polls Telegram updates and strictly filters against alert trigger timestamp."""
    timeout = 120
    start_poll = time.time()

    while time.time() - start_poll < timeout:
        updates = requests.get(f"https://api.telegram.org/bot{bot_token}/getUpdates").json()
        for result in updates.get("result", []):
            msg = result.get("message", {})
            msg_date = msg.get("date", 0)
            text = msg.get("text", "").strip().upper()

            # Only process messages sent AFTER the incident started
            if msg_date >= (alert_start_time - 5) and text == "YES":
                return True
        time.sleep(3)
    return False


Once authorized, healer.py programmatically mutates the .env config and restarts the container via the Docker socket:
# agent/healer.py
import docker

def apply_remediation_and_restart(service_name: str, key: str, value: str):
    # Step 1: Mutate the configuration parameter
    with open(".env", "r") as f:
        lines = f.readlines()
    with open(".env", "w") as f:
        for line in lines:
            f.write(f"{key}={value}\n" if line.startswith(f"{key}=") else line)

    # Step 2: Execute the Docker restart via host socket binding
    client = docker.from_env()
    container = client.containers.get(service_name)
    container.restart()
    return True

The biggest takeaway from this build: context quality is everything. By explicitly tagging OpenTelemetry spans with StatusCode.ERROR and http.status_code, I gave Gemini real, structured facts instead of ambiguous log strings. The quality of the root-cause analysis was night and day compared to my first attempt with raw log text.
The second thing genuinely surprised me: always timestamp your HITL guardrails. During testing, the agent was auto-restarting containers the instant it received a new alert — it turned out it was finding a YES I'd sent 10 minutes earlier for a completely different incident. A 5-second timestamp offset filter fixed it. Obvious in hindsight, two hours wasted finding it.
The last one I'll carry into every future project: observability is not optional for autonomous agents, it's the foundation they run on. Without SigNoz bridging raw OTLP traces into queryable ClickHouse, the agent would have nothing factual to feed Gemini. The AI is only as trustworthy as the data underneath it.
If I rebuilt this today, I'd replace the Telegram polling loop with SigNoz's own webhook payload as the authorization token — a cryptographically verifiable approval chain instead of plain-text YES matching. I'd also expose a /status endpoint on the agent so SigNoz dashboards can show the current remediation state in real time, closing the feedback loop entirely inside the observability platform.

### The Need for Autonomous Systems in Modern Infrastructure

As organizations scale their digital infrastructure, the demand for high availability and rapid incident response becomes increasingly critical. Traditional monitoring tools can alert teams to issues but often lack the capability for proactive remediation. Autonomous self-healing systems, driven by artificial intelligence (AI) and sophisticated observability frameworks, address this challenge by not only identifying problems but also resolving them autonomously. This capability significantly reduces the mean time to recovery (MTTR) and enhances overall operational efficiency.

### Observability: The Backbone of Self-Healing Mechanisms

Observability serves as the foundation for any self-healing system. It refers to the ability to monitor and understand the internal states of a system based on the data it generates. Tools like SigNoz provide real-time insights into application performance through distributed tracing, metrics, and logs. The quality of this telemetry data is critical; without it, AI-driven systems risk making erroneous decisions that could worsen existing issues. For instance, if the observability data is noisy or incomplete, the AI may misdiagnose a problem, leading to inappropriate remediation actions.

To illustrate, consider a scenario where an application experiences intermittent downtime. If the logs are incomplete or the metrics are not accurately captured, the AI might incorrectly attribute the issue to a network problem rather than a resource exhaustion issue. This highlights the importance of maintaining high-quality observability data, as it directly influences the efficacy of the self-healing mechanisms.

### AI-Driven Root Cause Analysis: Beyond Traditional Monitoring

Integrating AI into observability tools allows for advanced root cause analysis (RCA) that transcends traditional error logs. Machine learning algorithms can sift through vast amounts of telemetry data to identify patterns and anomalies. For example, if a spike in HTTP 500 errors correlates with a surge in database latency, a well-trained AI model can recommend specific actions, such as scaling database instances or optimizing connection pools. This predictive capability enables organizations to mitigate issues before they escalate, effectively transforming incident management from reactive to proactive.

A practical case study involves a retail application experiencing a sudden increase in user traffic during a sale event. The AI system analyzes the telemetry data and identifies that the database queries are taking longer than usual, correlating with the increase in traffic. By preemptively scaling the database instances, the system can maintain performance and avoid downtime, showcasing the power of AI-enhanced RCA.

### Designing the OmniSRE Agent: Architecture and Functionality

The OmniSRE agent acts as the brain of the autonomous system, interfacing with both the application and the observability stack. Its architecture must ensure that it operates independently of the monitored services to maintain resilience. A Docker container setup is employed, allowing the agent to access the Docker socket for executing remediation actions. Below is a simplified Docker Compose configuration:

```yaml
version: '3.8'

services:
```

This configuration ensures that the OmniSRE agent can issue commands to restart services or scale deployments without being affected by the failures of those services. Additionally, the agent can be configured to log its actions and decisions, providing an audit trail for accountability and further analysis.

### Implementing Human-in-the-Loop (HITL) Safeguards

While automation enhances operational efficiency, it also introduces risks, particularly when AI systems have unchecked access to critical infrastructure. Implementing a Human-in-the-Loop (HITL) mechanism is essential for maintaining control over automated actions. In the OmniSRE system, a Telegram bot serves as the HITL interface, requiring human approval before executing any remediation actions. This dual-layered approach mitigates the risk of erroneous auto-remediation while still allowing for rapid response times.

For example, when the OmniSRE agent identifies a potential issue, it sends a formatted diagnostic card to the Telegram bot, detailing the problem and proposed remediation steps. The human operator can review this information and either approve or reject the action, ensuring that critical decisions are not made without oversight.

### Testing and Validating the Autonomous System

Rigorous testing is crucial to validate the functionality and reliability of the autonomous system. Simulated chaos engineering can be employed to inject failures into the system and observe how the OmniSRE agent responds. For example, by triggering a simulated database failure, one can monitor the system's ability to diagnose the issue and execute the appropriate remediation actions. Key metrics to track during these tests include MTTR and the accuracy of the AI's RCA.

In practice, conducting chaos tests can reveal potential weaknesses in the self-healing capabilities. For instance, if the system fails to restart a service in response to a simulated failure, it may indicate the need for further tuning of the AI model or the remediation processes.

### Real-Time Incident Handling: A Case Study

To illustrate the effectiveness of the OmniSRE agent, consider a scenario where a simulated database failure is injected into the system. As the chaos is unleashed, SigNoz alerts the OmniSRE agent, which processes the telemetry data to diagnose the issue. The AI model identifies a connection pool exhaustion problem and recommends a service restart. The agent then sends a formatted diagnostic card to the Telegram bot for human approval. If approved, the agent modifies the configuration and restarts the service, demonstrating a complete closed-loop remediation process.

This case study highlights how the integration of AI and HITL mechanisms can create a robust incident response framework, significantly reducing downtime and improving service reliability.

### Future Directions: Scaling with Kubernetes and Advanced AI Techniques

As organizations scale their infrastructure, transitioning from Docker to Kubernetes can enhance the resilience and manageability of self-healing systems. Kubernetes offers built-in mechanisms for scaling and self-healing, making it an ideal platform for deploying autonomous agents. Future iterations of OmniSRE could leverage Kubernetes Custom Resource Definitions (CRDs) to manage the lifecycle of services and automate scaling decisions based on real-time telemetry data.

Moreover, incorporating advanced AI techniques, such as reinforcement learning, could further optimize the decision-making processes of the OmniSRE agent, allowing it to learn from past incidents and improve its responses over time.

### Conclusion: The Future of Autonomous Systems in DevOps

The integration of AI-driven observability and self-healing mechanisms represents a significant advancement in DevOps practices. By leveraging tools like SigNoz and implementing robust architectures, organizations can create systems that not only detect issues but also resolve them with minimal human intervention. As we continue to refine these technologies, the potential for fully autonomous systems becomes increasingly tangible, promising to transform the operational landscape of modern software engineering. The journey toward autonomous self-healing systems is not just about automation; it's about creating resilient infrastructures that can adapt and respond to challenges in real-time, ultimately leading to enhanced operational excellence.
